## Architecture Overview

**Sleeper Train Map** — interactive visualization of European night sleeper train routes on a Leaflet map. Built with Next.js 15, React 18, React-Leaflet, and Tailwind CSS 4.

### Data Flow

1. **App Entry:** `pages/index.js` → `<Layout>` component manages global UI state (`isGrouped`, `showRoutes`, `hideIntermediateStations`, `layerType`), persisted to localStorage.

2. **Data Fetching:** `useInitialData()` loads in **two stages**, because a first paint is worth more than a complete one on a slow connection. Stage one is the single `/api/initial-data` request the map cannot draw without; the hook renders from it and flips `isLoading` false. Stage two then fetches the route polylines (`/api/route-geometry`) and the PKP/RJ GTFS bundles in the background and re-assembles the same state with them merged in — `assemble()` is pure and total, so it runs identically with or without them. The hook uses **module-level caching** (1h TTL) shared across all component instances, and that cache holds the in-flight *promises* too, so React 18 strict mode's double mount joins one request instead of fetching the payload twice. The API endpoints set CDN cache headers (`s-maxage=3600`).

3. **Map Rendering:** `DynamicMap.js` is loaded with `next/dynamic` + `ssr: false` (Leaflet requires browser APIs). It consumes `useMapMarkers()` and `useRoutePaths()` hooks that memoize expensive computations.

4. **Station Selection:** Clicking a marker sets selected station state → filters related routes → `TrainBottomBar` and `TrainDetailPanel` display journey details.

### The source registry (no hardcoded operators)

`data/sources/registry.json` declares every data source: which adapter scrapes it (`scripts/adapters/{adapter}.mjs`), what file it writes (`public/data/scraped/{output}`), and how its trains merge into the map payload (the `synthetic` config consumed by `build-initial-data.mjs`: id prefix, agency, station aliasing, BoT dedup strategy). One subtlety worth knowing when `synthetic.excludeBotMatched` is on: a **bare** train number is only unique within an operator (BoT carries a CFM/CFR 401 and an SJN 475 next to European Sleeper's ES 401/475), so such sources declare `synthetic.botMatchAgencies: ["ES"]` to say whose rows may legitimately match — absent means "any row", which stays right for operator-prefixed keys like `"NJ 403"`. Rows carrying the source's own `idPrefix` never count as coverage either, so the scrape runner's leftover rows can't shadow the richer row the merge builds. Both rules are covered by `npm run verify-synthetic-scope`. **Adding an operator = adding a registry entry** (+ an adapter module only if no existing kind fits: `backontrack`, `json-api`, `html`, `gtfs`, `static-config`, `osm`, `canonical-routes`, `xml`). Every enabled entry also declares `endpoint` — the concrete address it reads, so the integration dashboard can print `https://content.amtrak.com/content/gtfs/GTFS.zip` rather than "official GTFS"; nothing in the pipeline consumes it, and where `params.feedUrl`/`params.baseUrl` exists the validator forces the two to agree so the documentation cannot drift from what the adapter fetches (`verify-registry`). The scrape runner, the merge, `/api/operator-trains`, `/api/data-status`, and the admin dashboard all iterate the registry. Schema + validation: `scripts/lib/registry.mjs`; editable in the admin "Registry" tab (server re-validates before committing).

Additional per-entry capabilities (all optional, all registry-driven):

- **`trusted: true`** (requires `official: true`) — the source's data bypasses the review queue: new routes/stations it corroborates are auto-approved by the nightly classifier (see below). `trustConfig(registry)` in `scripts/lib/registry.mjs` derives the trusted prefixes/source ids.
- **`enrich`** — post-scrape view-map enrichment (`scripts/lib/enrich-view-map.mjs`, called from the runner's `finalizeViewMap`): updates matched BoT rows in place from official data. Strategies: `trainsByNumber` (match by `trip_short_name_0/1` against the source's trains file; options `setPolyline` + `polylineMode: legacy|perDirection`, `updateVia` (+ `viaOnlyIfRicher`, which refuses a stop list shorter than the row's own), `setTimes`, `stamp`, `agencyIds`; `registry.mjs` enumerates them all, since an option read by name means "off" when misspelled) and `gtfsBundle` (match via `pkpEntryForRoute` endpoint validation against `params.statusFile` — reused train numbers carry corridor `variants` picked by endpoint match, and compound labels stitch through-car legs at their junction, mid-corridor switches included; options `updateVia`, `stamp`, plus `geometryFallback` = OSM-backed polylines from `route-geometry.mjs` for rows the bundle can't corroborate — geometry only, never a stamp). `stamp` writes `official_sources: [sourceId]` onto the row — the classifier's corroboration signal. `updateEndpoints` replaces the row's `origin_trip_*`/`destination_trip_*` with the feed's first/last stop and `updateServiceDays` its `service_id_*` — both opt-in, for sources whose feed *is* the operator's timetable. They matter more than they look: Back-on-Track still called European Sleeper's ES 474/475 "Berlin Hbf" while the operator ran them out of Berlin-Spandau and into Berlin Gesundbrunnen, so the row's own polyline reached a different place than its endpoint marker — and `getStationTimesForTrain` (`src/lib/seo/stationTimes.js`) validates endpoints before accepting a feed's stop list, so the Berlin–Paris connection page silently lost its whole timetable. Slugs are city-based (`cityForStation`), so `/connections/berlin-to-paris` is unchanged; the legacy `/trains/` slug does change, which is what `npm run build-redirects` appends (old URL keeps resolving). Durations live on the *trip*, which enrichment never touches, so `routeDurationMinutes()` (`src/lib/seo/format.js`) measures them from the row's endpoint times whenever the row carries `official_sources` — across the published payload that corrects exactly the two rows whose stated duration contradicted their own times (ES 452 15h23→16h27, ES 474 18h32→17h05). Sources with `trainsByNumber` + `synthetic` also get raw-file synthetic leftover rows (the old NJ-only behavior, generalized).
- **`runner: "external"` + `command` + `schedule`** — registry-scheduled script steps that run inside `npm run scrape` (e.g. `pkp-gtfs` runs `npm run parse-pkp-gtfs` daily so the bundle is fresh before enrichment). `schedule: weekly` = Mondays or any `workflow_dispatch`/`FORCE_ALL_SOURCES=1` run.
- **`pkp-plk` supplements PKP station info** (`kind: json-api`, enabled): the official PLK "Otwarte Dane Kolejowe" API (`pdp-api.plk-sa.pl`, `scripts/adapters/pkp-plk.mjs`, auth via the `PLK_API_KEY` scrape secret) is the infrastructure manager's authoritative planned schedule, and its stop lists reach across the border (Berlin/Praha/Wien), adding the international station names GTFS's Polish feed lacks. It has no coordinates or track geometry, so instead of a synthetic/enrich source it **folds** its per-train stop lists (station names + times; coords reconciled from GTFS by city, foreign stops stay coordless — fine for the station-list text) into the existing `pkpTrainShapes.json` `byTrainKey` bundle, keeping the GTFS/OSM polylines. It fetches all IC trains in one bulk `/schedules?carriersInclude=IC` pull and matches bundle rows by train number **or** endpoint cities (international trains carry a national number ≠ the commercial EC/EN number). It also enriches Back-on-Track PKP rows the Polish GTFS doesn't carry (through-car routes like Warszawa–Rijeka): matched by oriented endpoints, it sets the detail-panel station list (`pkp_schedule_*`) plus `via_*` on the row — `via_` makes `deriveCities` link those stations to the route (map dots) and `buildAllRoutesPaths` chain them into the line, all from Back-on-Track coordinates (PLK has no geometry of its own). PLK emits station names ASCII-folded or in alternate forms (`Bohumin`, `Graz Hauptbahnhof`), so both the bundle fold and the GTFS-less row enrichment canonicalize every emitted name to its BoT spelling via `data/overrides/station-aliases.json` (`canonicalizeStationName`) — otherwise the international stops wouldn't match BoT's coordinate-bearing stations and would drop from the map dots and route line. Runs after `pkp-gtfs` (which regenerates the bundle nightly) and re-applies every run, but is gated on the `/api/v1/data-version` `schedulesVersion` GUID so a typical night is a single request (respects the hourly rate limit; caps via `params.maxRequestsPerRun`). Field reads are centralized in the adapter's `FIELDS` map (schema confirmed from live responses; the no-auth `/fields/schedules` endpoint documents it).
- **`europeansleeper` takes stops and times from the operator's own timetable, geometry from GTFS.** https://www.europeansleeper.eu/timetable is what European Sleeper stands behind, and it disagrees with the feed: the feed runs ES 474 out of Berlin-Spandau at 17:52, the operator out of Berlin Gesundbrunnen at 17:25, and Spandau appears nowhere on the page. `scripts/lib/es-timetable.mjs` parses it (plain server-rendered HTML, no framework payload) — the format's trap is that the **bold time is the departure at every stop except the last**, where it is the arrival, with intermediate arrivals in a trailing `<i>`. Service days come from prose, but only from sentences naming their train ("Train ES 452 … departs on Tuesday, Thursday and Sunday"); the Brussels–Milan paragraph names no number, so 400/401 keep the feed's days. `mergePageOverFeed()` in the adapter lays page over feed per train: **page** supplies stops/times/days, **GTFS always** supplies the polyline, the validity window and the December `future` period. The page's date picker is JS-driven and cannot be selected over GET (`?departure-date-sql=…` is ignored; the route `<select>` uses opaque ids like `value="8"` for ES 400), so a nightly fetch sees only trains running *now* — 400/401 stay on GTFS until the Milan service starts and upgrade by themselves. The fetch is never fatal: any failure logs and falls back to GTFS, so a page outage costs the operator's times, not its trains. Parser covered by `npm run verify-es-timetable` against committed real markup (`tests/fixtures/es-timetable/`), the merge by `npm run verify-es`. The sandbox has no egress to that host, so page-sourced data only appears after a scrape runs where egress is open.
- **`europeansleeper` runs off the Mobility Database GTFS feed mdb-3107** (`kind: gtfs`, enabled): `scripts/adapters/europeansleeper.mjs` downloads `mdb-3107/latest.zip` — MDB's self-updating alias, the same object its "Download latest" button serves, so a nightly job tracks the feed instead of pinning a snapshot (`params.fallbackUrls` carries the second MDB hostname; the dated `.../mdb-3107-YYYYMMDDHHMM/...zip` URLs are immutable and must not be used). Routes are taken per `data/sources/europeansleeper-sleepers.json`, matched on `route_short_name` ("ES 452"), and keyed by **bare number** ("452") because BoT view-map `trip_short_name_*` is bare. The feed ships `shapes.txt`, so ES no longer touches `scripts/lib/route-geometry.mjs`. It reuses `downloadGtfs`/`loadGtfsDir` from `scripts/lib/gtfs.mjs` but **not** `buildSleeperTrains`, because this feed is date-expanded — one trip and one `service_id` per operating date, `calendar_dates.txt` only, past dates retained, and each date free to carry its own diversion and shape. So the adapter: filters to trips still running on/after today; **splits them at the European timetable change** (the second Sunday in December) into the period running now and the one that replaces it; within each period picks the **modal** stop sequence (the generic "most stations" rule selects diversions that run once a year) and unions weekdays across every run in that period. Splitting matters — read as one window, ES 400 advertised four weekdays for a 3×/week train and showed December's routing four months early. The upcoming period rides along as `future` and `appendSyntheticRoutes` gives it its own row (`es_400_from_20261214`, `draw_as_active`, `"… (from 14 Dec)"`), which is what retired the hand-authored `future-route-previews.json` entry; it is emitted only when the new period changes the days or the endpoint **cities**, so a mid-route stop swap doesn't draw a near-duplicate line. The adapter also wraps `>24h` times and emits them `T`-prefixed (`enrich-view-map`'s `toHHMM` matches `/T(\d{2}:\d{2})/`), and canonicalizes station names at emit time via `station-aliases.json` so `updateVia`'s raw names still link stations to the route. Numbering follows the operator: the feed's ES 400/401 (Brussels–Milano) supersedes Back-on-Track's stale 456/457, whose row `240` is retired in `data/overrides/disabled-routes.json`. In `TrainDetailPanel`, the feed supersedes BoT for **every** European Sleeper train it carries, not just the synthetic rows: the panel keys ES off the trip's agency as well as the `es_` route prefix (the enriched BoT rows 237/238 have real trips and so never reach the synthetic fallback path), and prefers the feed's stop list, endpoint names, times, duration and service days over BoT's copy — BoT still routes ES 452 via Dresden Neustadt/Berlin Hbf, and its 15:23 duration contradicts the feed times the row already carries. Trains the feed does not carry (ES 454/455, postponed) keep BoT's values. The row itself is corrected the same way by the enrichment's `updateEndpoints` + `updateServiceDays` (below), so the map, the bottom bar and the connection pages agree with the card.
- **`europeansleeper` also prices every night of the next six weeks, last-minute deals included** (`params.fares`, `scripts/lib/es-fares.mjs` + `es-last-minute.mjs` + `es-fare-calendar.mjs`). European Sleeper is an affiliate route, so its fares get the Intercity Notte treatment and one more layer. **Regular fares** come from the operator's own booking API (`europeansleeperprod-api.azurewebsites.net/api`, no key): `POST /search/trains` answers three consecutive nights per call (which nights the train runs, and its `routeId`), `POST /search/availability` prices one night per place type and fare level (Easy / Good / Flex Night). About 1⅓ requests a night, so all six trains × 42 nights (~340 requests, `searchesPerRun` 300 nights) are re-read **every** night rather than a slice at a time — the calendar is as fresh as the scrape. Only what a standard adult can buy is priced: passenger type 72, seats left out (the map shows beds), **women-only compartments left out** (the Young/Senior rule from `lefrecce.mjs`), a sold-out fare level never prices its class, and a private couchette compartment keeps its own class (`privateCouchette`) because its price is for the whole compartment. Station ids are the curated `operator-booking.json` map first (the same ids the Book button uses), then the operator's own `/constants` list by folded name — bilingual names read either half, and anything ambiguous is null rather than a fare for the wrong station. A curated id `/constants` does not list is not trusted, and an end the operator does not sell becomes the operator's own terminus **in the same city** on a route that also serves the other end (`endpointsFor`): the first live probe found the timetable running ES 474/475 to Berlin Gesundbrunnen while `/constants` lists only Berlin Hbf and Ostbahnhof and its Paris route ends at Berlin Hbf, so those two are priced to/from Berlin Hbf. It is deliberately not "the nearest stop inward": our stop list for 475 has no Berlin Hbf, so that rule would have priced Paris → Hamburg-Harburg, a shorter journey at another fare. No unique same-city terminus means no fare. **Last-minute deals** are why this is not just the operator's fare finder: couchettes on trains 1–3 weeks out at a flat €40/€60 a bed (€160/€240 a whole compartment), sold from per-direction landing pages (`params.fares.lastMinute.pages`, each naming the train it sells, plus any `/last-minutes-…` page the `/last-minute` index links to) and **not shown in `/fare-finder`**. A deal's date is only on its landing page. The first probe run (2026-10-01) showed six pages — four `/last-minutes-…` plus `/last-minute-switzerland-milan` (ES 401) and `/last-minute-cologne-brussels` (ES 400) — each with a CLASSIC and a CLASSIC PRIVATE tab and one `<button name="price" value="1062">` per deal reading "Fri 02 Oct 26 · €40 p.p." (a two-digit year after the month; `p.p.` = a bed, a bare €160 = a whole compartment), and deals as close as tomorrow rather than the advertised one to three weeks. That markup was first parsed blind, so `parseLastMinutePage` stays layout-agnostic and strict like `jr-sunrise.mjs`: it finds deal ids in any form shape (`<button>`/`<input>` named `price`, `<select name=price>` options, `data-price-id`, `/receipt/price/N/id` links, script JSON), dates one only from its own label or the nearest date heading before it (never a sibling deal's date), and drops what it cannot date. Each deal's price is confirmed against `GET /receipt/price/1/{id}`, whose empty answer means expired. A deal lands in the night's `classes` as `lastMinuteCouchette` / `lastMinutePrivate` beside the regular ones, with `deal.landing` naming where it is sold — so `cheapestNight`, the facts tile and the plan index all see it as the night's price without learning anything new. Deals are stripped and re-read every night (a sold-out one must not linger); when no landing page can be read at all, yesterday's are kept one day at most. On the connection page `FareCalendar` marks deal nights amber with a ⚡, opens with a banner ("Last-minute deals from €40 on N nights — up to X% below the regular fare … not in European Sleeper's own fare finder") whose button jumps to the cheapest, and a deal night's card shows the deal against the same night's regular fare for the same kind of place (`nightDeal`, `src/lib/lastMinuteDeals.mjs`: savings, "Cheapest fare this night" only when it undercuts every regular place, a compartment's per-person split), the operator's terms, and **Get this deal** → the landing page through the affiliate redirect (`dealsUrlTemplate`, `buildDealsLandingUrl`); the regular **Book** button becomes secondary and opens the booking engine on that night (`urlDateSuffix` `departureDate=yyyy-MM-dd`). Grid cells now print whole units — "119.99" did not fit a 320 px cell. **Flash sales are the second programme on the same mechanism** (`params.fares.flashSale`): `/flash-sale` (2026-10-01: "Shared Classic for €49 one-way … selected November and December departures … Book by 6 October") is an index of six per-direction offer pages (`/flash-berlin-paris`, …) plus links to its own translations (`/de/flash-sale`, skipped), so `fetchDeals` reads each programme's index, takes its offer links (`findOfferLinks`), and ties a page to its train where the registry does not say: by a whole route in the link text (`trainForOfferText`, "offer from Brussels and Cologne to Switzerland and Milan"), else by the address (`trainForOfferPath`) — the live index's links read only "to Brussels and Paris", so the route is in the slug, read as an exact first-city–last-city pair and checked against that "to …" text. Exact, because the last-minute slugs name a stretch instead (`/last-minutes-hamburg-berlin` sells Paris → Berlin) and must read as no train rather than a wrong one. Matching runs on each train's first and last city via `cityForStation`, unique or nothing. **A deal past the horizon is dropped, never re-dated**: a deal's date is the nearest date label before its button (its own text is the price alone), and the first flash scrape picked that nearest date among the *in-window* ones only, so with a 60-day horizon the December Mondays all read as Monday 30 November. The nearest date is now chosen among all of them and one out of range drops the deal (`outside`, counted in the log); the horizon is the calendar's own `days`. And a deadline is never a heading (`DEADLINE_CUE`): every offer page opens "Offer ends 6 October" right above its list, which is the date that 60-day horizon actually handed the Milan → Brussels page's 14 December. With both fixes the first refresh (2026-10-01) put flash deals on 116 nights across all six trains, every one a night the booking API also prices. Flash deals land as `flashSaleCouchette` / `flashSalePrivate`, the night's `deal` carries `programme` and `until` (the sale's last booking day, `saleEndDate`), and a sale past its end adds nothing. Because those dates are months out, European Sleeper's calendar covers **92 nights** (`params.fares.days`, ~740 requests a night at `searchesPerRun` 600) rather than the shared 42. **A class's "from" is that class's own cheapest night**: `cheapestNight` returns per-class minima with `classDates` (and `dealLanding`), not the classes of the night that won overall — the first ES calendar's cheapest night was a €40 deal for the next day, when the regular couchette cost €159.99, and the map panel printed "Couchette from €159.99" for a train whose couchettes start at €59.99. In `TrainDetailPanel` the fares list **regular** classes only and is kept to four rows (`panelFareRows`): Couchette, Bed in 3-bed cabin, Bed in 2-bed cabin, Private compartment (a cabin's figure is one bed's, since the API prices one adult, and both the panel and the calendar labels say so) — each the cheapest of its group (standard and Comfort cabins fold together by beds, single cabins are left to the connection page's calendar) on that group's own night, dated where the nights differ; a fare without European Sleeper's cabin classes lists exactly as `fareClassRows` does; the Fare line quotes the regular fare (`splitDealFare`); and the deal sits in the booking block beside the deals link (`BookingActions` `deal`), linking to the page that sells it. Never fatal: a fare failure costs the fares, not the trains. Neither host is reachable from a dev sandbox, so the readers follow the operator's OpenAPI notes and synthetic markup (`verify-es-fares` says which); label the PR `run-probes` for `probe-es-fares` and `refresh-data` to see the real calendar on the preview before merging.
- **A bare train number is only unique within an operator — on the render side too.** The registry guards the scrape with `synthetic.botMatchAgencies`; the same rule has to hold wherever a feed keyed by bare number is read back. `src/lib/europeanSleeper.mjs` (`esScheduleForTrip`) is that guard for the detail panel: without it Back-on-Track's CFM/CFR **401** (Chişinău–București) and SJN **475** (Trondheim–Bodø) rendered European Sleeper's stops, endpoints, duration and service days, because the ES feed is keyed `400 401 452 453 474 475`. `src/lib/seo/stationTimes.mjs` solves the same problem the other way: it keeps **every** feed that claims a number and lets endpoint validation choose, instead of the first file `readdirSync` returned — first-wins was silently costing 14 Nightjet/EuroNight timetables on the connection pages (Zürich–Praha among them), since the shadowing feed then failed validation and the timetable was dropped rather than replaced. Its endpoint check runs both sides through `resolveCanonicalStationName`, so a feed's exonym ("Prag Hbf") validates against the route's canonical name, and emitted stop names are canonicalized so one page cannot spell a station two ways. Covered by `npm run verify-european-sleeper` and `npm run verify-station-times`.
- **`cfr` (CFR Călători, Romania) reads the national timetable as GTFS, because the XML it is published as cannot be fetched** (`kind: gtfs`, `adapter: cfr-gtfs`, enabled, `trusted: false` until a night's log on main confirms the counts).   Three things shape the adapter, and each shipped broken once before it was right. **The feed keys trains its own way** — `route_id` IS the train number and `route_short_name` is `"IR-N 346"`, while the row it must land on is labelled `"D 346"` — so the allowlist gained a fourth entry kind, `{ route | routes, name }` (`gtfs.mjs`), which matches a feed route by its own name and keys the train by Back-on-Track's. Unlike `{ from, to, name }` it deliberately never reads endpoints, because a feed truncated at a border states endpoints that are not the train's. `routes` lists the legs of a **through car** — `"IRN 472/IRN 1743"` is one journey under two numbers — joined by `stitchLegs` at the last station they share, with each leg's geometry cut there: leg one runs *past* the junction (472 carries on to the Hungarian border), so a plain concatenation draws the line to Curtici, jumps back to Arad and sets off again. The junction keeps leg one's arrival and leg two's departure, which is what a through car actually does there. **Legs go in journey order, not label order** — row 13's `"IRN 1954/R 8824"` runs Mangalia→Suceava, so its legs are `["8824", "1954"]`. **The feed stops at the national border** (346 ends at Lokoshaza, 401 starts at Ungheni, 460 at Ruse), so `cfr-gtfs` splices Back-on-Track's foreign stretch back on: head is every chain station before the first one the feed carries, tail every one after the last. Without it `updateVia` *replaced* Budapest and Győr with nothing and published D 346 as "București Nord → **Wien Hbf**, arriving **03:00**" — Lokoshaza's time on Vienna's marker, with the drawn line ending at the frontier. Strictly worse than the stale data it replaced, and nothing downstream complains. It surfaced only because `SCRAPE_ONLY=cfr` reproduced it: the runner hydrates `ctx.shared` from disk **after** the source loop, and a full run only works because `backontrack` happens to run first — so the adapter reads the committed view map itself rather than depending on either accident. A spliced-in station with **no coordinate is kept**, with a null location: four of row 28's Bulgarian via names (Svilengrad, Stara Zagora, Veliko Tarnovo, Gorna Oryahovitsa) are text in a via string and nothing else, absent from the station table entirely, and dropping them made the "richer" official list *shorter* than the one it replaces, so `viaOnlyIfRicher` refused the whole train. Everything downstream that needs a position already checks for one.

  **The endpoint check is what makes `setTimes` safe here**, and it is deliberately strict: a folded name comparison (so "Cluj Napoca" matches "Cluj-Napoca" and cedilla-ş matches comma-ș) and nothing looser. A city-level fallback was tried and removed — it fired on none of the 36 entries, and the one case it would have changed is one it must not, since Budapest Keleti and Budapest Kelenföld are different stations. Because a spliced train ends where its row ends and carries the row's own endpoint times on the foreign ends, writing times back corrects the Romanian end and no-ops the other: **4 endpoint times change, all domestic** (the clearest being IRN 1822, departing Arad 17:15 rather than Back-on-Track's 17:30), and **no international endpoint moves**. `updateEndpoints` stays **off**; `updateServiceDays` is **on**, and the reasoning is worth keeping because the first answer here was wrong. The feed dates its calendars honestly and **13 of the 42 IR-N routes had finished their season** by mid-September (the summer Black Sea trains, Jun–Sep), so the windowed `serviceDisplayForServices` answers `null` for them — true and useless, since the row then keeps Back-on-Track's "2026: Daily". The row schema turned out to have a perfectly good word for a season: `parseBotServiceString` reads `"2026/06/13-2026/09/06: Daily"` and `parseBoTServiceIdDateRange` acts on it. So `seasonalServiceDisplay` (`gtfs.mjs`) renders a part-year service from its own dates, in the **trips** spelling with a year on both sides — `renderCalendar` emits a shorter `"2026/06/13-09/06"` that only `calendar.mjs` understands, and picking the form the map can act on is the whole point. The result is narrow by design: **31 of 38 directions unchanged, 7 rewritten, every one of them seasonal** — including rows 13 and 25, where Back-on-Track was still carrying a **2024** season two years later. `seasonalOrYearlyDisplay` wraps it, because the first cut dropped the year on the 28 year-round directions to fix the seven wrong ones (`"2026: Daily"` → `"Daily"`), and a bare weekday list parses to a calendar with no validity at all.

  **Saying the season is only half of it; something has to read it.** `isRouteOutsideServiceIdSeason` hides a route whose window has closed, but it walks **trips** — the upstream Back-on-Track export that nothing in the pipeline writes to — so an enrichment that corrects the row cannot reach it. `routeSeasonHasClosed(route)` is the row-reading twin, mirroring `routeHasNotStartedYet` for the other end of the window, consulted **first** because a corrected row is better evidence than an export nobody updates; the row is threaded through all seven call sites as an optional argument, so callers without it behave exactly as before. A row counts as closed only when **every** direction it states is closed. The blast radius is one route: 125/136 and 13/25 were already hidden, and **26 (Constanța–Oradea) was drawn as a daily service nine days after its last run**. **The reason it slipped through took a detour through North America to fix, and the order was the whole lesson.** Its string was `"2026/06/11-09/06"` — the short season spelling, with no year on the end — and `SERVICE_ID_CALENDAR_RANGE_RE` demanded a year on both sides, so it fell through to "cannot parse, therefore runs". **88 service strings across the payload are written that way**, and widening the regex hides 17 more routes, so the obvious one-line fix was measured before it was made — and the measurement stopped it. Amtrak's rows carried windows that were not seasons at all (`City of New Orleans: 2026/09/13-09/16`, `California Zephyr: 2027/03/13-03/13: Sat`), because `gtfs-sleeper` rendered **one representative trip's** `calendar.txt` row and Amtrak splits a daily train across many short-dated services. Widening the parser first would have retired two year-round daily trains. So the source was fixed first: `buildSleeperTrains` now unions the services of every trip describing the same train, **grouped by `direction_id`** — a rung settled by two live refreshes rather than by reasoning. Unioning the whole route folds both directions and made the Cardinal (3×/week each way, on different days) read six weekdays; grouping by `trip_short_name` instead fragments, because Amtrak numbers runs finely enough that one number can hold a single dated trip, and the California Zephyr came back as one Saturday — the very fault being removed. Direction is coarse enough not to fragment and fine enough to answer; `trip_short_name` is the fallback for a feed without it, the whole route after that, and SNCF and Entur populate neither so they sit where they always did. `seasonalServiceDisplay` also had to stop taking its weekdays from the two endpoint dates, which is right for a `calendar_dates` feed like Romania's and wrong for a `calendar.txt` one: a daily summer service came out "Fri, Sat", whichever days its season began and ended on. With the strings rewritten against the live feed — every Amtrak and VIA route now reading as its operator publishes it, Cardinal "Tue, Thu, Sat", Vancouver–Toronto "Wed, Sun" — the regex was widened. The honest count is **18 routes stop being drawn, of which 14 are pre-existing** — HŽPP 3/48, PKP 10/113/137/267/268, PKP/ČD 265/266, MÁV 223/224, ST 73/80 and CFR 26 — every one of them a summer or spring service whose stated window closed between 1 August and 7 September, drawn as running into mid-September. Note the four trains Back-on-Track numbers 12641/12642/12941/12942 were **renumbered** to 1641/1642/1941/1942 in the current timetable; the allowlist maps them, `route` being the feed's number and `name` staying Back-on-Track's. Covered by `npm run verify-cfr-gtfs`, which pins each of the three faults above as well as its fix, and by `probe-gtfs --verify-allowlists`, which now includes `cfr` — it exercises allowlist matching (the thing December rots) but not the splice, so a probe run reports the internationals ending at the border. The GTFS host is reachable from a dev sandbox, so unlike SNCF and Entur this source can be run and reviewed before merging.

  **A shared feed is not a shared operator, and `IR-N` is a category rather than a company.** The first cut of this source filtered the feed by `route_short_name.startsWith("IR-N")` and shipped ten new Romanian night routes; **four of them were not CFR's**. mdb-3236 is the national aggregate, so Astra Trans Carpatic (agency `237330`, a private operator) files its București–Arad service under the same `IR-N` category as CFR (`6100826`) — and `cfr_IR-N_11500` therefore drew a second copy of the route Back-on-Track already carries as row **24, correctly attributed to ATC**, under CFR's name, CFR's booking link and CFR's timetable page. It is opt-in per registry entry: a single-operator feed (Amtrak, VIA, European Sleeper) has no second agency to confuse and gains nothing from declaring one. The four ATC entries are out of `cfr-sleepers.json`, leaving 42.

  **Removing an allowlist entry does not remove its route, which is the other half of that fault.** `appendSyntheticLeftovers` only ever appended, and a synthetic row is baked into the committed view map — so the two ATC rows survived the allowlist edit, the scrape, the canonicalize and the parity test, all of which agreed the data was fine. It now **withdraws** first: any row carrying the source's `idPrefix` whose every `trip_short_name_*` is absent from the freshly scraped trains is deleted before the append, so a train the source stops claiming stops being published (`[scrape] cfr: withdrew 2 synthetic row(s) whose train is gone: cfr_IR-N_11500, cfr_IR-N_11502`). It is scoped to the prefix and to a source that scraped at all, so a night where an operator's feed fails does not empty its routes — the sticky-trains merge still holds those for seven days, and withdrawal reads the merged result. The retired slug's redirect is repointed by `build-redirects` the same way a disabled route's is; `/trains/constanta-to-arad-ir-n-11502` now lands on `/connections` rather than on a page the build no longer emits.

  **A feed route is an address, not a possession, and two rows can live at it.** South of Ungheni the Kyiv–București sleeper (UZ **099/100**, row 174) *is* the Chișinău–București one (CFM/CFR **401/402**, row 22): the Kyiv cars run attached to the Chișinău train, which is why both rows state the same București times to the minute — arrive **06:38**, depart **19:06** — and why the feed carries one train where Back-on-Track records two. - **A probe you cannot run is a probe you do not have.** `workflow_dispatch` only fires for a workflow file that is on the **default branch**, so a new probe is unrunnable until its own PR merges — which is backwards, since the probe exists to tell you whether the thing in that PR works. Both price/GTFS probe workflows therefore also declare `pull_request: types: [labeled]` with the job gated on `github.event.label.name == 'run-probes'`: a `pull_request` trigger runs from the PR head, **including a workflow added in that same PR**, so labelling the PR runs the probe on the branch and the log can be read before anything merges. Gated on the label rather than on every push because these download whole GTFS feeds. Note that workflow inputs do not exist on a `pull_request` event — every `${{ inputs.x }}` needs a literal fallback or it renders empty (`--limit ""` → `Number("") === 0`), and `probe-gtfs` therefore reads the *event* rather than an input. A `pull_request` run does **both** of its questions: the catalogue sweep (which of the catalogued feeds are real, and what is in them — the question you ask *before* an allowlist exists, and the only path that fetches a feed with no registry entry yet, so it is how a fix to a failing catalogue feed gets tested before merging), then `--verify-allowlists` (every committed `gtfs-sleeper` allowlist through `buildSleeperTrains` against its live feed, printing the trains it built and naming any entry that matched nothing, so a new or drifted allowlist fails there instead of in the nightly scrape after a merge). Verify runs last so a log tail carries it. A dispatch runs whichever one its inputs name, and naming `--url`/`--source` wins over both. `allowlistVerifiableSources()` is what picks the entries: `gtfs-sleeper` only, since European Sleeper reads GTFS through its own date-expanded adapter and would report drift that does not exist. `HOST_HEADERS` in `gtfs.mjs` sends per-host request headers — and *only* to a host with an entry, keyed by hostname, because several feeds work today and none should be risked for one that does not; `verify-na-gtfs` pins that safety property rather than any fix, asserting the three working hosts are still fetched with no headers at all. The one entry is `rata.digitraffic.fi` (VR), whose terms ask a client to identify itself, and it is worth recording what that did **not** buy: the 406 that host answers with survived a `Digitraffic-User` plus an explicit `Accept` of `application/zip, application/octet-stream, */*`. That also rules out content negotiation — no server honouring `*/*` can refuse it — so the 406 is a generic rejection and the catalogued **URL** is the suspect, which puts VR in the same bucket as VY/ZSSK/HŽPP: a wrong address, not a hostile server. Do not send more headers at it. **Two parse ceilings, because a feed's two heavy files fail differently.** `stop_times.txt` past `MAX_STOP_TIMES_BYTES` means the timetable itself will not fit, so the probe reports the size and skips the feed — which is the finding that says "use the per-operator file". `shapes.txt` past `MAX_SHAPES_BYTES` (200 MB, clear of Amtrak's 17 MB) costs only geometry, so `loadGtfsDir` skips *that file* and `buildSleeperTrains` falls back to the station chain per trip — the feed stays fully usable, which matters because Entur ships **416 MB** of shapes for Vy against 7.6 MB of stop_times and 2.6 GB for the national aggregate, and `readCsv` reads a whole file into one string before splitting it: parsing that is what OOM'd the first Entur run. `gtfs.shapesSkipped` is reported rather than left to look like a feed that never had geometry. And the crash was invisible — `node … | tee` makes bash report *tee's* status, so the step stayed green — which is the same failure this whole area is about, so both probe steps now `set -o pipefail`. **"Nothing found" has two causes and only the route list separates them** — the heuristic missed the trains, or the trains are not in this file — so a feed yielding ≤1 candidate now prints its own agencies and route names. It earned that immediately by correcting me: I had concluded from a bare candidate count that Entur's `rb_vyg` held only Vy's Oslo commuter network, and the route list shows **F4 Oslo S–Bergen** sitting right there among the 24. The trains were never missing; the probe had **two** faults hiding them. First, `isOvernightCandidate` guarded GTFS's hours-≥-24 notation but not the other way a feed says "next day" — Entur writes Oslo S 23:03 → Bergen 06:23 as `06:23`, so `arr - dep` came out **negative** and every Norwegian night train read as no night train, which is the exact bug this function exists to prevent, pointing the other way; an arrival earlier than its departure now counts as overnight and `length` is measured modulo a day. Second, even with that fixed the *representative* trip on a national line is a day train, because a night train is one trip among thirty day services — so `selectRouteRuns` keeps the fullest **overnight** trip alongside the representative and the table reports that one, while `dayTrainWarning` still says a plain name or pair entry would select the day train. **`catalogueFeeds` also skips what the sweep has nothing left to learn from**: a source marked `status: "broken"` cannot start working until somebody edits its url, and `sweep: false` is for one that works and is deliberately unused — Entur's national aggregate, whose 3.5 GB re-download was three quarters of the sweep's four minutes for a single "too big" line.
- **A source you cannot see the output of is a source you have to merge to review.** The probes above make a branch's *logs* readable before merging; this is the same thing for its *data*. The enrichment that puts an official stop list on a Back-on-Track row happens inside `npm run scrape`, which runs nightly against main — so a branch that adds a data source changes the pipeline and nothing a Vercel preview can show. You open the preview, see Back-on-Track's three via points exactly as before, and the only way to learn whether the source works is to merge it and wait for 03:00 UTC. `SCRAPE_ONLY` (a comma-separated list of registry ids, read by `selectSources()` in `scrape-data.mjs`) plus **"Refresh branch data"** (`.github/workflows/branch-data-refresh.yml`) close that: label a PR `refresh-data` — a *different* label from `run-probes`, because this one **commits** — and it scrapes what the branch touches, canonicalizes, rebuilds the redirects and pushes the result to the branch, so the PR's own preview serves the real payload. `scripts/changed-sources.mjs` is what "touches" means, read off the registry rather than hardcoded: a source's own entry changed (compared per id against the base ref, since a text diff of one big JSON file cannot say whose entry moved), its `params.configPath` allowlist changed, or **any module its code reaches** changed — which selects every entry sharing them, so a `gtfs-sleeper` edit refreshes Amtrak, VIA, SNCF and all three Entur feeds rather than only the one whose allowlist moved. That last rule once matched the adapter's own file and nothing else, and it made the whole mechanism miss most of what it exists to catch: nearly all of the pipeline's logic lives in `scripts/lib/`, every adapter but two imports it, and a branch fixing how SNCF's service days are read edited `scripts/lib/gtfs.mjs` — so the labelled run went green in 45 seconds saying the branch touched no source. An entry's code is now its whole **import closure** (`moduleClosure`): follow relative specifiers — `import`, `export`-less side-effect imports, `require`, even one inside a JSDoc type — from its entry point until they stop resolving to repo files. It reads specifiers with a regex rather than a parser, deliberately: the error that costs is under-selection, since over-selection only scrapes a source that needed no fetch. An entry with `runner: "external"` has no adapter at all, so its closure starts at the script its `command` runs, resolved through `package.json` — which is how an edit to `parse-pkp-gtfs.js` selects `pkp-gtfs`. Closures stay tight (1–10 files each, 37 across all 18 enabled sources, 7 ms to build), so this is a selection and not a floodlight: `scripts/lib/gtfs.mjs` picks the eight GTFS readers and leaves NightJet, ČD and Back-on-Track alone. And because "nothing to scrape" is the one answer you cannot check by reading it, the script now prints the files it weighed and how much code would have counted whenever it selects nothing. A filtered run does **not** re-fetch the critical source: `hydrateSharedFromDisk` reads the committed Back-on-Track files instead (the same fallback the adapter already uses when its own fetch fails), because pulling a fresh copy writes ~10 MB of unrelated upstream churn into the branch and buries the one thing under review. Enrichment over an already-enriched view map is idempotent, which is what makes that safe. It paid for itself on its first run: the Entur sources looked finished, and the branch preview showed the enrichment resolving **0 of 168** via stations to a coordinate, then 27 of them landing in the wrong country, then a Norwegian quay id on a European Sleeper row — three faults that were all one merge away from main. Note the canonicalize step is the run's first reviewer, and it had to learn something too: `"<id> trains present but no <prefix> routes built"` reads as a broken source and is one for NightJet or Amtrak, but for a source that only *enriches* zero synthetic routes is the healthy answer and the best one — all eight Entur trains matched a Back-on-Track row, so the assertion failed the whole publish on a completely successful scrape. It now counts enriched rows too (`enrichedRowCount`, in agency scope, by `trip_short_name`) and logs them as `entur-sjn 0+2e`, which still fails loudly on the real fault: train keys drifting out of step with Back-on-Track's labels. SNCF would have hit the same assertion its first night on main.
- **`sncf` (SNCF, France) addresses a night train by where it runs, not by its route name** (`kind: gtfs`, `adapter: gtfs-sleeper`, enabled, `trusted: false`): the SNCF Open Data GTFS export is the cheapest official source left on the board — a plain zip, no key, TGV/Intercités/TER — and it carries all nine of our SNCF routes. What it does not carry is a usable route name: `route_long_name` is `"-"` (short name `INCONNU`) for **six** of the eleven Intercités de Nuit, and two of the named ones are named *wrong* (Albi–Paris filed under `"Paris - Latour-de-Carol"`, Aurillac–Paris under `"Paris - Rodez / Albi"`). Since `buildSleeperTrains` keys its output by route name, those six would have collapsed onto the key `"-"` and five would have vanished into the last write. So an allowlist entry may now **name the train it selects**: `{ from, to, name }` matches endpoints in that order only, picks the fullest trip running that way, and keys it by `name`. Orientation is load-bearing because one SNCF `route_id` holds both directions plus the portions that split at Toulouse and Brive — "the fullest trip on this route" answers a question nobody asked — and two oriented entries give the two directions their own stop lists and times. Naming also puts the key where the enrichment looks: these are Back-on-Track's own `"IC Nuit NNNN"` labels, so `trainsByNumber` lands the feed's stop list on the row it belongs to instead of drawing a second copy of the route. The route-name path keeps a collision guard (`claimKey`) so a duplicate long name can no longer silently eat a train. **A named entry must also run past midnight**, because a sleeper allowlist has no use for a day train and taking one is worse than taking nothing: the fullest Paris Austerlitz → Toulouse Matabiau trip in this feed is the 08:27 Intercités via Limoges, and the first live run picked exactly that — it would have replaced the night train's Montauban routing with a different corridor under the night train's own number. **Enrichment is via-only, deliberately.** BoT gives these routes 2–5 via points and the feed gives 8–16 — more map dots, a better-drawn line, a real station list on the connection pages — and every stop between two fixed endpoints is on the corridor whichever trip was picked. `viaOnlyIfRicher` guards the exception: the feed carries the Paris–Aurillac portion as a 3-stop stub whose single via station would have displaced BoT's three, so official wins only where it is also more complete (off by default — European Sleeper's shorter list is authoritative and *should* replace BoT's). Times and days are a different bet, and the first run settled it against them: endpoint times disagreed with BoT by over an hour on four of ten runs (a through-portion waiting to be joined), and `frequency` came out per-**trip** — "Sun" for a daily train — because a date-expanded feed gives each trip its own `service_id` and only one trip is picked. **The days half of that took two goes, and the first one is the instructive half.** `resolveNamedTrips` keeps the fullest trip for the stop list and the times, but collects the `service_id` of **every** trip that matched the entry, and `serviceDisplayForServices` unions them — calendar.txt weekdays and calendar_dates.txt dates alike — so a named entry reports the train's timetable rather than one run's date. The single-trip answer was visibly incoherent on the first live run: IC Nuit 3740 read "Mon, Tue, Wed, Thu, Fri" while IC Nuit **3731**, the other direction of the same service, read "Sun". **The union alone is not enough, and the live run said so: it returned "Daily" for 14 of 18**, Paris–Latour-de-Carol and Paris–Cerbère among them, which Back-on-Track has as weekend services. "Daily" is the worst shape this fault can take, because it is indistinguishable from the truth — and **Back-on-Track has eight of the eighteen as daily** (Paris–Nice, –Briançon, –Toulouse, –Rodez, both directions each), which are the year-round trunk services and are very likely right. Note this is not the feed *corroborating* them — a source that answers Daily for fourteen of eighteen agrees with any Daily by default, and that is worth naming rather than counting as two witnesses. So the earlier note here that "no Intercités de Nuit runs daily" was simply wrong, and Back-on-Track's days are in better shape than that claim implied. **The first explanation tried was seasonal spillover and it is recorded here because it was wrong**: a year-wide union genuinely does saturate that way, and a window genuinely does fix it (`serviceWindow`, below) — but the windowed SNCF output came back *byte-identical*, because this export's dates already sit inside one period. A fix that is right in principle and changes nothing in practice is worth writing down as exactly that, or the next reader credits it with the numbers. **The second explanation was how a named entry matches, and the probe killed that one too — with the finding that actually settles it.** `resolveNamedTrips` matches on endpoints plus "runs past midnight" and never reads `trip_short_name`, so a corridor carrying a second overnight service would hand it to whichever entry names that corridor and the union would report both trains' days. `stats.namedMatches` was added to test that (per entry: trips, services, date span, and the distinct feed `trip_short_name`s — several numbers under one entry being the signature), `probe-gtfs --verify-allowlists` prints it against the live feed, and the answer came back **`(feed carries none)` on every one of the eighteen**: SNCF's export populates no `trip_short_name` anywhere. So the signature cannot fire, and the fix it was meant to justify is impossible — there is no train number in this feed to match on. **That is the real ceiling: an endpoint-matched entry in a feed with no train numbers cannot be shown to address one train**, and one train with several service patterns is indistinguishable from two trains sharing a corridor (the entries took 2–23 trips each; one `service_id` can itself carry many dates, so trip counts do not settle it either). Stop lists survive that completely — they come from **one** trip, the fullest, which is why via-only enrichment was the right first win and still is. Service days do not: they are a union over everything that matched. So `updateServiceDays` stays off for SNCF not pending more evidence but as the conclusion, and the probe now prints that warning whenever a feed carries no train numbers at all, so the next such feed is met with the ceiling already known. Entur is in the same position (also no `trip_short_name`), and shows the same symptom mildly: SJ Nord's 405 reads "Mon, Tue, Wed, Thu, Fri, Sun" against 406's "Daily" on the same corridor. `decemberTimetableChange`/`nextTimetableChangeAfter`/`currentTimetableWindow` now live in `gtfs.mjs` — moved out of `europeansleeper.mjs`, which met the same fault first (ES 400 advertising four weekdays for a 3×/week train) — and `buildSleeperTrains` takes `serviceWindow`, defaulting to the period running now. A calendar.txt service is counted only where its own `start_date`/`end_date` span overlaps the window; an undated one is kept, since the window exists to exclude what it can prove belongs to another season, not to drop a service for being undated. The window is an injected argument rather than read from the clock inside, or a test pinning real dates would start failing on a calendar date instead of on a code change. The overnight filter in `resolveNamedTrips` is the third guard — a day train sharing the corridor must not lend the night train its weekdays. Covered by `verify-na-gtfs` against a hand-built date-expanded fixture, which pins the **fault** as well as the fix: the same seasonal feed read with `serviceWindow: null` must still come out `"Daily"`, and each period read on its own must give that period's days. `updateServiceDays` stays **off** for SNCF as a settled conclusion, not a pending one: the feed cannot attribute a day to a train, fourteen of eighteen read Daily, the two directions of Aurillac disagree (Thu–Sat against Fri–Sun), and the value of the field is small next to the cost of being wrong about when a night train runs. So `setTimes`/`updateEndpoints`/`updateServiceDays`/`stamp` stay off, and without a stamp `routeDurationMinutes()` keeps measuring from the trip rather than from endpoint times that may not be the train's. The feed has **no `shapes.txt`**, so geometry would be the station chain (or OSM) — another reason the first win here is stop lists. `params.canonicalizeStationNames` is opt-in on the adapter because it only helps a feed whose stations are also in BoT's table under another spelling: a via station becomes a map dot only when a coordinate-bearing stop of that exact name exists, so `"Nice-Ville"` has to become `"Nice Ville"` (`station-aliases.json`); Amtrak and VIA stay off it, their stations not being in that table at all. Covered by `npm run verify-na-gtfs`; the committed allowlist is checked against the live feed by `probe-gtfs --verify-allowlists` (see the probe bullet above), and stays empty in the repo until a scrape runs where egress is open.
- **`sncf` also carries SNCF's own fares and punctuality, read from SNCF's open data rather than its booking site** (`params.openData`, `scripts/lib/sncf-open-data.mjs` + `sncf-open-data-pass.mjs`, called from `gtfs-sleeper` after the trains are built). SNCF Connect has no public API and sits behind bot protection, so there is no per-night fare to read the way European Sleeper's or Trenitalia's calendars do; what SNCF *does* publish, on `ressources.data.sncf.com` (Opendatasoft, ODbL), is two datasets that answer the next two questions a traveller has. **"Tarifs Intercités"** (`tarifs-intercites`) is the standard-fare (tarif plein) range — a minimum and a maximum — per origin–destination and class, day and night Intercités alike, revised with each tariff change (the current one from 2 January 2026). Each train's two ends are matched by UIC code (the GTFS stop ids end in it: `…-87547000`; `uicKey` drops the check digit so a 7-digit column matches too), falling back to folded names, and the reverse pair is accepted because a full fare does not depend on direction. **Only berths are priced, and a berth is what `type_place` says, never the bare class.** The first live run (2026-10-04) settled the shape: 2 559 records, columns `transporteur, origine, origine_uic8, destination, destination_uic8, classe, profil_tarifaire, type_place, prix_min, prix_max`, classes only ever `"1"`/`"2"`, and each night pair three rows — class 2 from €19 (a seat, `type_place: "assise"`), class 2 from €29 (the 2nd-class couchette), class 1 from €39 (the 1st-class couchette). So class "2" is a seat *and* a couchette, and the first cut, which looked for "couchette" in the class label, priced nothing at all — correctly refusing rather than quoting the €19 seat. `type_place` is what separates them (`couchetteSecond` / `couchetteFirst`, "Couchette, 2nd class" / "Couchette, 1st class"); a row whose class and place type say nothing is *reported* in the log, not priced. `transporteur` names the service ("Intercités de nuit à réservation obligatoire" / "… de jour …"), and where it does only the night rows are read: Paris–Toulouse carries a day train's €15 seat and €20 1st class beside the night train's rows. Restricted profiles (Avantage, Jeune, Senior, Enfant, réduit, abonnement…) never set the floor (`isStandardAdultProfile`, the lefrecce rule). The train gets `fare: { fromPrice, classes, classMax, basis: "tariff", tariffModified }`; `stampOfficialFares` carries `classMax`/`basis` onto `fare_{dir}`, `fareClassRows` prints such a class as its range (**"€39–€79"** rather than "from €39"), and both the panel and the connection page say whose range it is (`fareBasisLabel`: "Standard adult fare as published by the operator; it moves with demand within this range"). **"Régularité mensuelle Intercités"** (`regularite-mensuelle-intercites`) is the AQST's monthly count, per pair it selects, of trains scheduled, run, cancelled and late at the terminus (15 minutes for a journey over 3 h — every night train). It is attributed to a night train **only where no daytime Intercités runs the same pair**: the count is per pair, not per train, so a Paris–Toulouse rate is mostly the day trains'. `dayServedStationPairs` (`gtfs.mjs`) reads that off the feed the adapter already loaded — every pair some trip that does not cross midnight runs between — and those pairs get no figure at all. The trailing 12-month figure is summed from counts rather than averaged from rates, and the train's own direction is used (Paris→Briançon and Briançon→Paris are separate rows). The live dataset runs about five months behind (in October its latest month was May), so "recent" is judged against the dataset's own latest month — a train may trail it by one month (`MAX_LAG_BEHIND_DATASET`), which is what drops Paris–Latour-de-Carol, last reported in February — with a 12-month absolute cap. A joined train is filed under both its ends ("ALBI/RODEZ → PARIS-AUSTERLITZ"), so either half of a `/`-joined name matches, but only when no row names the pair exactly (Cerbère has its own row and a pre-2022 "TOULOUSE-MATABIAU/CERBERE" one). The first live run gave 10 of 18 trains a figure; the rest are Paris–Toulouse (day trains share it), Latour-de-Carol (not reported since February), and Albi's Sunday portion until the joined-name rule. It lands as `punctuality_{dir}` on the row (`stampPunctuality`), page-only (`stripPageOnlyFields`), and renders under the fares in `RouteTimetable` ("72% on time — 13 of 18 trains in May 2026 arrived within 15 minutes of schedule… 63% over the last 12 months", with the dataset linked) and as an FAQ question ("Is the Briançon to Paris night train on time?", only when there is a figure, `punctualityAnswer` in `src/lib/punctuality.mjs`) — not in the meta description (see the snippet rollout below). Both datasets are fetched nightly (one ~800 KB JSON each) and are never fatal: a night the portal is down carries last night's fares for 30 days (`carryPreviousFares`) and punctuality for 45. **The reader was first written blind** — `ressources.data.sncf.com` is unreachable from a dev sandbox — so it resolves columns by what their folded labels say (`origine_uic8` and "Gare origine - code UIC" alike) and refuses rather than guesses; `verify-sncf-open-data`'s fixtures now follow the live layout the probe printed, and mark the few values it did not (a berth row's `type_place` is assumed to read "couchette"; a different live value lands in the scrape log as unpriced, with the value named). Label the PR `run-probes` for `probe-sncf-open-data` (every class/profile value with the classifier's verdict, every AQST pair, which of ours a day train shares, and what each train would get) and `refresh-data` for the real figures on the preview.
- **`entur-vy` / `entur-sjn` / `entur-goa` (Norway) are one integration in three files** (`kind: gtfs`, `adapter: gtfs-sleeper`, enabled, `trusted: false`): Norway is centralised on Entur, which publishes a GTFS file per operator **codespace** with no key — `rb_<codespace>-aggregated-gtfs.zip` in `storage.googleapis.com/marduk-production/outbound/gtfs/`. Three tokens cover all four Norwegian night routes: `vyg` has **F4 Oslo S–Bergen** (BoT row 69, 605/606), `sjn` has **F6 Dovrebanen** and **F7 Nordlandsbanen** (rows 70/71, 405/406 and 475/476), `goa` has **F5 Sørtoget** (row 65, F5 725/726). The national aggregate `rb_norway` is real and unusable nightly — 807 MB of `stop_times`, 2.6 GB of `shapes` — so it carries `sweep: false` rather than being re-downloaded to print one "too big" line. **Every allowlist entry is a named oriented pair**, for the reason SNCF needed them and more sharply: Entur files each night train *inside a whole line that also runs day services*, so the trip with the most stations — what a plain route name selects — is a day train, and only a named entry scans every trip and requires it to cross midnight. Enrichment is via-only with `viaOnlyIfRicher`: BoT gives these four routes 2–6 via points against the feed's full stop list, and the branch run that first showed those stop lists in a preview is what caught the two things standing between them and a map dot. **Entur appends " stasjon" to every station name** where the rest of the dataset writes the bare name, so `params.stripStationSuffixes: [" stasjon"]` takes it off before `canonicalizeStationNames` runs the remainder through the alias table — without it **0 of 168** via stations resolved to a coordinate-bearing stop and the richer stop list bought nothing at all (84 of 86 resolve after the strip; the two airport stations are the alias table's job, "Oslo lufthavn" → "Oslo Airport Gardermoen"). The strip is registry-driven and opt-in because it is only safe where it cannot collide: **no** station in BoT's 29 747 is named "… stasjon", so there is no correct name for it to destroy, and the next feed's suffix has to earn the same check. `stationNameCanonicalizer()` in `gtfs.mjs` composes the two and is shared with `probe-gtfs`, so the probe cannot report names the scrape would not write. **And 27 of the 86 stations then land on a Back-on-Track coordinate somewhere else entirely** — every one stamped country NO while geocoded across Europe: Tverlandet on the Basque coast, Stjørdal in Czechia, Voss in Germany, Trondheim Airport Værnes in Stockholm. Nothing had shown it because a station no route names never gets a marker to be wrong in. `station-coordinates.json` now carries the operator's own coordinate for each, and the threshold is not a judgement call: the 59 that agree agree within 1.26 km and nothing at all sits between that and 5.31 km. `enrich.agencyIds` is scoped to `["VY","SJN","GA"]` and that is load-bearing: a bare **475** is also European Sleeper's Brussels–Prague train, the collision documented above. Geometry is the station chain, since every one of these feeds ships 108–416 MB of `shapes` and `loadGtfsDir` skips a `shapes.txt` past `MAX_SHAPES_BYTES`. Covered by `npm run verify-gtfs-probe`; the committed allowlists are checked against the live feeds by `probe-gtfs --verify-allowlists`.
- **`trafiklab` (Sweden) reads the national GTFS, and it is the first feed here that says which trains are sleepers** (`kind: gtfs`, `adapter: trafiklab-gtfs`, enabled, `trusted: false` until a night's log on main confirms the counts). Trafiklab's GTFS Sweden 3 is Samtrafiken's aggregate of every Swedish operator, fetched with the `TRAFIKLAB_API_KEY` scrape secret (`?key=`, passed in both `scrape-data.yml` and `branch-data-refresh.yml`); Bronze allows 60 requests per 30 days, so one download a night fits and a retry loop would not. The same feed is re-hosted daily without a key as Mobility Database **mdb-2939** (`mobilitydata-datasets-prod/mdb-2939/latest.zip`, the alias European Sleeper and CFR already read), which is `params.fallbackUrls`: a missing, revoked or exhausted key costs a log line, not the source, and it is also how the feed is inspected from a dev sandbox, which cannot reach `opendata.samtrafiken.se`. Night trains are **route_type 105** ("Sleeper Rail Service") with the train number as `route_short_name`, so the allowlist (`data/sources/trafiklab-sleepers.json`) is a list of numbers — and route_type is part of the match, because SJ also files a *seated* twin of train 1 under 100. That makes this source unlike SNCF and Entur in the way that matters: a service day belongs to **one** train, so `setTimes`, `updateEndpoints` and `updateServiceDays` are all on. Four things shape the adapter. **It is too big for `readCsv`**: stop_times.txt is 698 MB (past V8's string limit) and shapes.txt 2.4 GB, so `streamZipCsv` (`gtfs.mjs`) pipes `unzip -p` through readline with a key pre-filter and the whole read takes ~7 s; the rail shapes turned out to be the stop coordinates again (3–17 points per run), so shapes.txt is never read and the line is the chain through the official stops. **It is date-expanded and full of engineering works** — SJ 1 alone is 28 trips over eleven weeks — so a train is its **modal** stop pattern weighted by dates (among patterns within **0.9** of the heaviest — a near tie — the one with most stops: Snälltåget lists every night twice, once as the Berlin–Malmö sleeper portion and once as the through train, and they tie; at half the heaviest SJ 2 came out calling at Helsingborg, which it skips most nights), its times the most-run **(first departure, last arrival) pair** of that pattern (a works period nudges intermediate stops by a minute and splits the usual timetable into fragments that a whole-timing vote lets a diversion outvote), and its days the weekdays it runs on across the timetable period (a weekday under a quarter of the busiest one's runs is a works detour, not a service day). **The feed ends at the next timetable change**, so the span of a train's dates is not its season: `renderServiceDays` calls a train seasonal only when it stops well short of the horizon every other train reaches, and takes the season's start from the row when the feed begins mid-season — without that, Snälltåget's summer Jämtland train would have published an eleven-day season. **Its stops abroad are a Swedish traveller's view**: the Berlin train comes through with no Hamburg although the operator serves it, so `fillForeignGaps` puts back Back-on-Track stations that are outside Sweden and fall between two stations both carry — never a Swedish one (the feed is the authority there) and never one within 15 km of a neighbour (Berlin Hbf is not a stop before Berlin Gesundbrunnen). Station names go through `makeStationNamer`, which tries the dataset's spellings ("Umeå Centralstation" → "Umeå C", "Härnösand Central" → "Härnösands central", "Södertälje syd station" → "Södertälje syd övre") and **accepts one only where its Back-on-Track coordinate lies within 3 km of the feed's**: "Boden" sits 2 271 km from Boden there and "Stockholms central" 1 164 km from Stockholm, the Norwegian geocoder failure again. So `alignLabelsWithRows` hands each row direction the train that runs that way when both labels are reversed, keeps the operator's number on the train as `feedRoute`, and logs it; the cost is that the row still shows Back-on-Track's labels. What it changed on the payload of 2026-09-26: rows 62, 63, 77, 79 and 81 are stamped, with 7–17 official stops per direction against 3–9; **SJ 1/2 run Sunday–Friday**, not daily; row 81 was one train with another's times — Back-on-Track labelled 91/92 "Luleå" with 93's times, the feed runs 91/92 **Stockholm–Umeå** — and **93/94 Stockholm–Luleå** had no row at all and is now `trafiklab_93`; Snälltåget's Stockholm–Berlin runs to the horizon six days a week instead of closing on 1 November; the Jämtland train's season ends 3/4 October, not 27/28 September. The adapter logs every route_type-105 route the allowlist does not list — SJ's 60070/70070-style works portions and Snälltåget's one-off Malmö–Narvik charter 20/21 are expected there, anything else is a new night train. **The usual timetable is not every night's, and the works are the difference.** GTFS Sweden 3 carries no works notices as text (those live in the separate GTFS-RT ServiceAlerts product, which needs its own key), but every diversion is in the static feed as a dated trip — SJ 93 runs 10 stops via the inland line from 21 September to 2 October and reaches Stockholm at 12:13 on the 27th, exactly what sj.se shows for that night, while the card says 10:13 because most nights do. So `upcomingDeviations` writes, per train, the nights in the next 14 whose fullest run calls at a different set of stations or starts/ends more than 10 minutes off the usual clock (`deviations: [{date, from, to, departure, arrival, stops, skipped, added}]`); `groupUpcomingChanges` (`sourceFeedSchedule.mjs`) folds consecutive nights on one routing into a block and drops nights already past, since the file is rewritten nightly but read days later; and the panel renders it as "Timetable changes in the next 2 weeks" under the card, each night with its own clock and a search on the operator's site **for that date**. The dated link is `buildBookingUrl({ …, isoDate })`: an operator's `urlTemplate` may now set `dateFormat: "yyyy-MM-dd"` and `dateOffsetDays` (SJ: `sj.se/en/search-journey/choose-ticket-type/{origin}/{dest}/{date}/outward-journey`, `requireStationMapping` with `Luleå C` → `Luleå Central` and friends, so an unmapped station falls back to the booking page rather than a failed search), and `overrides-mutate` carries both keys through an admin edit. The booking CTA itself now searches the **corrected** row's endpoints (`officialRow.origin/destination`), not the trip's — SJ 91 starts in Umeå, whatever Back-on-Track's trip says. `TRAFIKLAB_GTFS_ZIP` points the adapter at a zip on disk. - **`nightjet` (ÖBB Nightjet / EuroNight) prices every night of the next six weeks from nightjet.com** (`params.fares`, `scripts/lib/nj-fares.mjs`, called from `scripts/adapters/nightjet.mjs` after the trains are built). The source is the **Train Price Search** behind nightjet.com's own destination pages — `GET /nj-booking-ocp/destinations/offers/{train}/{fromEva}/{toEva}/{ms}?forward=true&max=3` — the same `/destinations` family the timetable scrape already reads, with no token: it answers a train's next journey from a moment on with the cheapest offer per comfort class (`bestOffers.le` couchette, `.be` sleeping car, `.se` seat), one adult. The notes promise up to three journeys per call; **the first live run (2026-10-07, 360 calls) got exactly one every time**, so the budget assumes one and the reader takes any number. **The booking flow's `/connection` search is deliberately not used**: it now sits behind a SHA-256 proof-of-work captcha, which is why the weekly `nightjet-offers` probe answered `HTTP 400` on every run and Nightjet never had a price here, and solving an operator's anti-bot challenge is not something this map does. Request and answer shapes follow the reverse-engineered OpenAPI notes at martinlangbecker/night-train-apis and two open crawlers that read the same endpoint; nightjet.com is unreachable from a dev sandbox, so the reader is strict (a non-array answer, HTML, a journey whose departure is not an ISO date-time, or journeys only before the night asked about is an error, never "no train" — with one journey per answer an unreadable departure reads exactly like an empty answer, which would blank the rest of the window in one request; and `Date.parse` reads "08.10.2026" as 10 August, so `viennaDate` parses ISO date-times only) and `verify-nj-fares`' fixtures say they are synthetic. The first `run-probes` run (the generic `probe-prices:debug`, which prints price-like fields only) confirmed the shape — `[1 × { departure, arrival, bestOffers }]`, prices at `[0].bestOffers.{se,le,be}.price` — and the first `refresh-data` run priced **256 nights on 48 of 73 trains** with no failed request; of the other 25, 18 start after the window (the December, February and May timetables' numbers), four had nothing on sale from the first night asked (NJ 13464 and NJ 13466, the Feldkirch–Zürich portions, NJ 40246 and EN 50237), and three ran with no berth on any night reached (NJ 40421, NJ 493, and NJ 467, which starts on 15 October). **Berths only**: `le` → `couchette`, `be` → `sleeperBed` ("Sleeper, one bed" — the cheapest sleeping-car place that night, whichever cabin); a night selling nothing but seats is `none`. **The seat price is kept beside each night, never as a class** (`seat`, outside `classes`, which is all any price reader reads), together with the ÖBB product each figure is (`offers: { couchette: "Sparschiene" }`, the "inkl. Reservierung" every berth offer carries stripped): the product owner compared the calendar with shop.oebbtickets.at and suspected some couchette figures were seat prices, and with the seat on file that question is asked of every night read — a berth is a ticket plus a berth supplement, so one priced at or below its own night's seat is counted (`stats.suspect`) and named in a `[nj-fare] seat check:` log line every night. The scrape keeps such a figure as read, but **no reader quotes it**: `credibleClasses` (`src/lib/fareClasses.mjs`) drops it, and every reader of a night's price goes through it — `fareCalendarDays`, `cheapestNight` (the headline fare) and `/cheap-night-trains`. A night left with no credible berth is "unknown", not "no berth on sale". A figure is the cheapest of **every** product (Sparschiene, Sparschiene Komfort, Komfortticket, Standard-Ticket) and every couchette compartment (6-berth, 4-berth, ladies-only, comfort): the booking flow's own answer prices a couchette as the product's base plus the compartment's supplement (`refs` capture: Sparschiene 44.9 + 55 for a 6-berth, + 70 for a 4-berth), and the shop lists those side by side, so the product name is what a reader needs to find the same row there. The endpoint does not say when its cheapest couchette is in a ladies-only compartment (nightjet.com prices them the same as mixed ones). The calendar is the shared one (`fare-calendar.mjs`: 42 nights, `pruneCalendar`, `planFareSearches`, `cheapestNight`), keyed by the departure's **Vienna** date — every NJ/EN origin keeps Central European time, and each request asks from Vienna midnight of the night it needs (`viennaMidnightMs`, DST-safe). One answer settles more than the night it returns: a night it skips before the journey it returns has no train (the search runs forward), and an answer with nothing from that night on, or whose first journey is past the window (NJ 235 et al. start with the December timetable), makes the rest of the window `none` in one request — which is also how a renumbering shows up (NJ 13484 Graz–Zürich runs to 13 October and NJ 464 from the 14th, so one reads "nothing on sale from 2026-10-14 on" and the other prices from that night). **Except where the calendar knows better**: an empty answer turns only nights *without* a price into "no train" (`nightsProven`'s `held`), and nothing an answer infers overwrites what another answer said about a night that same run. The night asked about is always the answer's own. ### Integration dashboard (`/data` → Integrations)

The migration tracker: **which routes still come from Back-on-Track, what official source could replace it, and what to build next.** Today 172 of 291 routes (59%) run on a first-party automated source; 119 are still Back-on-Track across 28 operators.

- **The maths is one pure module**, `src/lib/integrations/model.mjs` (`.mjs`, dependency-free, raw-node testable — same reason as `operatorNames.mjs`). `/api/admin/integrations` is a thin reader over it; `IntegrationsTab` / `RouteSourcesTab` do one fetch and no arithmetic.
- **Route → source** (`resolveRouteSources`): `official_sources` first (the enrichment actually corroborated the row), then the longest matching `synthetic.idPrefix` (`nj_standalone_` must beat a shorter `nj_`), else `backontrack`. **Route → operator** is `splitAgencyIds(bot_agency_id || agency_id)` — `bot_agency_id` first because a synthetic row overwrites `agency_id` with the feed's own operator, losing the joint operator BoT recorded (`MÁV/ÖBB` → `ÖBB`), and the map and detail panel already resolve it that way.
- **Integration status is derived, never taken on trust from the catalogue.** "Found an official API" and "Pingwi fetches from it" are different claims, and the whole tool exists to keep them apart: an operator reads `integrated` only when a registry source with `official: true` is currently feeding ≥1 of its routes, `needs-maintenance` when that feed has gone stale/failing/disabled, and the curated status applies only when nothing official is flowing (where it cannot award itself `integrated`).
- **`data/sources/official-sources.json`** is the research catalogue: per operator a `website`, `countries`, `integrationStatus`, `difficulty`, `notes` and a list of concrete sources (`name`, `url`, `docsUrl`, `format`, `provides`, `auth`, `status`, `lastChecked`, `probeWorkflow`, `notes`). Planning data only — the scrape pipeline never reads it, and a source becomes real by getting a registry entry. Editable in the Integrations tab through the ordinary admin commit path (`official-sources` in `OVERRIDE_FILES`, actions `setOperator` / `setSource` / `removeSource`). `verify-integrations` rejects a source without an absolute, non-placeholder URL — the point is a link you can open, not a category.
- **Priority** ranks what to build next: `(botRoutes + 0.1 × botStations) × readiness (tested 1.0 / found 0.6 / none 0.15) × ease (easy 1.5 / medium 1.0 / hard 0.5 / unknown 0.9) × staleness`. `ease` exceeds 1 deliberately: a plain GTFS zip is a registry entry plus an allowlist because `gtfs-sleeper` already reads that shape, so SNCF's 9 routes outrank operators with more routes and no adapter. The "what to integrate next" shortlist skips operators with no source found (listed separately as "not actionable yet") and ones already integrated with ≥50% coverage — the table still bands everyone.
- **A fresh fetch is not fresh data.** Back-on-Track is scraped nightly so its timestamp is always green, which says nothing about whether upstream still maintains the route. Two artifacts close that gap, both committed by the existing daily workflow: `scripts/lib/classify.mjs` dates `lastChanged` on each seen entry (any fingerprint difference, stop-sequence drift included) and `canonicalize` projects it into **`public/data/published/route-history.json`** (~25 KB, so the 240 KB `seen.json` stays out of the lambda); the scrape runner persists the per-source errors it used to discard into **`public/data/scraped/source-health.json`** (`lastRunAt` / `lastSuccessAt` / `lastFailureAt` / `lastError` / `consecutiveFailures`, merged with the previous file). Both are optional inputs — freshness falls back to each artifact's own `uploadedAt`, and an entry with no `output` of its own (`pkp-gtfs` maintains the GTFS bundle) is dated from its `params.statusFile`, or it would read "never fetched" while visibly feeding 16 routes.
- **Tabs.** `/data` now opens on **Integrations**; **Route sources** is the flat 288-row table with the filters (the "Back-on-Track only" chip is the main one); **Routes** remains the map hide/show editor; **Review** keeps the proposal queue and its badge at the far end.

### Review queue ("all new data verified first")

Everything non-mechanical flows through a proposal queue the admin reviews in `/data` → Review tab. `/data`, `/api/admin/*`, and `/api/data-status` are loopback-only (`src/lib/localAdmin.mjs`): they 404 on Vercel and on any non-localhost host. There is no login.

- **Proposals** are single JSON files on the **`proposals` git branch** (`data/proposals/{pending,resolved}/`), metadata encoded in filenames so listing the queue is one GitHub Contents call. Envelope schema/codec: `src/pages/api/lib/proposals.mjs`. The branch never deploys (`vercel.json` → `git.deploymentEnabled.proposals: false`).
- **Producers:** nightly classifier (`scripts/classify-changes.mjs` + pure `scripts/lib/classify.mjs`), AI tasks (`scripts/ai-tasks.mjs`), price probes (`scripts/probe-prices.mjs`), and the public `/api/suggest` endpoint (honeypot + rate-limited; "Suggest an edit" in the detail panel).
- **The gate:** `data/canonical/state/seen.json` is the approval index. `buildInitialData({ seenIndex })` withholds viewMap rows / injected station markers not yet approved (default-allow when the index is absent so the map can never blank; canonicalize hard-fails if >10% of routes would be withheld). New route keys and stations are gated; updates to approved routes auto-apply, with FYI notes for material changes (days/endpoints/operator); vanished trains are retained 7 days (sticky merge in the scrape runner) then noticed once.
- **Trusted sources skip the gate:** routes whose key carries a trusted source's synthetic `idPrefix`, or whose row was stamped `official_sources` by the enrichment post-step, are auto-approved by `classify()` (`approved: true, autoApproved: <date>` in seen.json) — including previously-gated keys once corroborated. Stations injected by trusted sources auto-approve the same way (`stats.stationSources` from the build). Everything auto-added lands in ONE aggregate FYI `note` per night (dated `target.routeKey` so dedup can't block future nights). Disappearance notes are suppressed when a vanished key's trains all still run under another key (route-key migration). The workflow runs classify BEFORE canonicalize so auto-approvals go live the same night; a classify failure just gates new keys one extra night.
- **verify-build-parity** gates its build with the committed seen.json exactly like canonicalize. Any PR that changes merge inputs (registry, overrides, build code) must re-run `npm run canonicalize` to regenerate the published artifact, or the parity test fails.
- **Applying:** approval in the Review tab runs `planProposalApply()` (`src/pages/api/lib/proposals-apply.mjs`) — pure mutations committed to main via the GitHub Contents API (`src/pages/api/lib/github-content.mjs`). Apply kinds: `override.set` (reuses `applyOverrideMutation`), `seen.approve`, `route.add/update/remove`, `price.update`, `note` (no-op). Admin's own edits in the other tabs commit directly (the admin IS the reviewer).

### Curated routes & prices (data-only route coverage)

- `data/canonical/routes/{routeKey}.json` — admin-approved route files (created by `route.add` approvals). The `curated` registry source compiles them into the standard trains shape, so they flow through the same pipeline as scraped operators. Keys must be `curated_{trainName with _}`. New/changed curated routes appear after the next nightly scrape (or a manual `workflow_dispatch`).
- `data/canonical/prices.json` — per-route from-prices (from probes/AI/public, all reviewed). **An official, trusted source's own nightly fare outranks it**: `stampOfficialFares()` in `build-initial-data.mjs` stamps `row.pricing` (source = the registry id, `checkedAt` = the scrape date) from a `fare` on the trains of the source named by the row's `timetable_source`, taking the cheaper direction — the price analogue of trusted routes skipping review. `prices.json` is the fallback for routes no official source prices. Two sources write `fare` today: 12306 (all 54 China Railway routes) and Trenitalia's Intercity Notte through lefrecce.it (the `icn_` rows, see below). The bar is `official`, not `trusted` — trust lets a source create routes unreviewed, while a fare only ever lands on a row that already passed the gate. **A row's `pricing` is one figure; a card about one train needs that train's**, so the stamp also leaves `fare_0`/`fare_1` (`fromPrice`, `currency`, `seatClass`, `classes`, `checkedAt`) and `src/lib/fareClasses.mjs` is the one reading of them: `pricingForDirection` narrows the row's record to a direction (the `TrainDetailPanel` badge and "Fare" line, the plan index's legs, and the connection page's Book caption, which quotes the train its button opens rather than the cheaper direction — 12 of 113 per-train rows used to quote the return train beside an outbound button; a button that opens no train in particular, an operator homepage or European Sleeper's corridor page, quotes the route like the facts tile — and the `TrainTrip` structured data, whose node names direction 0's train and so carries that train's `AggregateOffer` or none) and, on a row priced per train (`hasDirectionFares`), never lends one train's figure to the other: a direction without its own fare keeps the fare model and shows no figure (`pricingWithoutFigure`) — the panel used to quote NJ 448's €84.9 on NJ 449's card, `fareClassRows` lists the berth classes cheapest first (the panel's "Fares" chips and `RouteTimetable`'s per-direction fares on the connection page, with the checked month). The panel picks the direction by train number (`fareDirectionForTrip`), not by its fuzzy `isDir1` origin match, and a synthetic trip reads the row's `pricing` — `fallbackTrips` builds trips from the row and carries none, which is why a stamped price never reached the panel. Covered by `npm run verify-chinese-12306`. Stamped onto viewMap rows + trips at compile time; consumed by the existing `getOperatorPricing()` route-first seam, surfacing as "from €X" badges with no component changes.
- **A price is worth four surfaces, and for a long time it reached none of them.** The pipeline is complete end to end — probe adapter → `probe-prices.mjs` → `price.update` proposal → review → `prices.json` → merge stamp → `getOperatorPricing()` — and it produced exactly one entry, for a route the published payload does not even carry, because of two silent faults. The NightJet adapter took `candidates.slice(0, sampleRoutes)` over a stably-ordered list, so every Monday sampled **the same 4 of 70** probe-able routes and the other 66 could never acquire a price however long the job ran; `selectProbeTargets()` (`scripts/lib/probe-rotation.mjs`) sorts by `routeKey` (the incoming order is whatever the scrape wrote, and a rotation over an unstable order is not a rotation), puts unpriced routes first, and advances a **full page** per run — `rotation * sampleSize`, not `rotation`, or week N+1 re-reads three quarters of week N — with leftover budget re-checking the stalest priced routes. And a probe that reached the API and extracted nothing filed zero proposals, which is byte-for-byte what a probe with nothing to report does, under a `continue-on-error` workflow step: invisible from every angle. `public/data/scraped/probe-health.json` (merged across runs like `source-health.json`, committed by the same workflow step) makes it legible via `consecutiveEmptyRuns`; errors *alongside* a price stay a partial run, not a failure. `probe.pricing` is now validated in `registry.mjs` — a typo in the adapter name used to fail at the dynamic import inside a try/catch and disable the probe silently — and `npm run probe-prices:debug` is the "Probe CFR source" equivalent for prices, calling the URL the nightly job calls through the adapter's own `buildProbeUrl` so the two cannot drift, and printing every field `collectPriceCandidates()` considered a price. Once a figure exists it lands on all four surfaces from that one number: the `RouteFactsGrid` "From" tile, the FAQ's "how much does it cost" question (which is simply *omitted* while the price is null — the highest-commercial-intent question on the page), the meta description (`Tickets from €39.` displaces the generic "Compare…" tail rather than being appended past where Google truncates), and an `AggregateOffer` on each `TrainTrip` — `AggregateOffer` because what the probe samples is a floor under a yield-managed range, with **no `url`**, since the booking link is an affiliate redirect and an affiliate URL does not belong in structured data. `offerFromPricing()` (`src/lib/seo/offers.mjs`) takes an already-resolved pricing record so the route→operator precedence stays in `getOperatorPricing()` and the snippet cannot quote a different figure than the tile. Note `scripts/adapters/regiojet-api.mjs` also exports `probePrices()` and is **not** wired to any registry entry — it needs per-pair station ids in `probe.pricing.pairs`. Covered by `npm run verify-price-probe`.
- `src/pages/api/lib/calendar.mjs` — canonical service calendar; parses BoT service strings and GTFS calendars, renders back to display strings, unparseable inputs round-trip verbatim. **Six shapes in the payload used to defeat it**, one of them the cross-year range `renderCalendar` itself emits — the module could not re-read its own output, and six legs arrived as unparseable notes for that reason alone. It now also reads `"Daily, except Sat"` (25 legs, fully determinable), a range with the year repeated on both sides, and the German `"Son"` for Sunday. **40 legs moved from a guess to a known weekday list, and no service string in the payload is unparseable any more.** The 52 that state only a cadence (`"Every 2nd day"`) are carried in a new `cadence` field rather than dropped into a note: the string says how OFTEN a train runs and never WHICH nights, so no caller may derive a weekday list from it and `availabilityFor()` must answer `unknown`. Rendering is a fixed point over all 70 distinct service strings in the payload — verbose inputs canonicalise (`"Saturday"` → `"Sat"`) rather than round-tripping byte-for-byte, which is what `verify-calendar`'s `stableRender` asserts.

### The trip planner (`/plan`)

**Two questions, one saved plan.** "I don't know where I want to go" (`/plan/amsterdam`) lists everywhere a sleeper could take you that night; "I know where I want to go" (`/plan/amsterdam-to-vienna/2026-09-18`) resolves the corridor, and when no single train covers it, offers chains of nights. A plan grows a city at a time — `/plan/amsterdam-to-berlin-to-prague-to-vienna/2026-09-18` — because the premise is that you do not know the whole route in advance.

- **The URL is the plan.** Cities in order plus the first departure date, with `?stay=2,1` for stopover nights. No account, no cookie, nothing about the person stored anywhere — copying the link is the save button, and that is worth saying on the page rather than only here. `src/lib/plan/url.mjs` is the grammar, dependency-free and `.mjs` for the same reason as `slugify.mjs`: the build, the client router and raw-node tests must produce the same string or a shared link resolves to a different plan than the one that was shared. The `-to-` separator is safe only while no city slug contains it (none of the 186 endpoint cities does); `verify-plan` fails if one appears, and `splitCorridor` takes the known-slug set so such a city degrades to a wrong-but-harmless split rather than two invented places.
- **`/plan` is the one indexable URL in the space.** Everything under it differs only by a date, which is an unbounded crawl trap, and its content already lives on the `/connections/` pages it links to. Parameterised plans carry `noindex, follow` and canonical `/plan`.
- **Availability is a tri-state, and that is the whole point.** 104 of the payload's 545 legs carry no operating days at all and 52 more state only a frequency ("Every 2nd day"), so **36% of the dataset cannot answer "does it run on the 18th"**. The tempting default is to let those through — the results page looks fuller — and it is how a planner told someone an Amsterdam–Milan sleeper leaves tonight when the row it read says "Postponed to 2027", carries no service string and has `00:00 → 00:00` placeholder times. `availabilityFor()` (`src/lib/plan/availability.mjs`) answers `runs` / `no` / `unknown` / `not-yet` / `suspended` with a `confidence` of `"pattern"` or `"none"`, every surface renders the difference, and the page says in prose what each badge means. Operator notes are read **before** the weekday pattern, because a note that says the service is on hold beats a timetable describing when it used to run. When date-level data arrives, `confidence: "timetable"` appears and nothing outside that module changes.
- **A route is two legs, never one.** The two directions have their own stops, times and operating days; ORing them (`service_id_0 || service_id_1`) offers the outbound on a night only the return runs.
- **Every stop is boardable, and that is what makes the product work.** Endpoint-to-endpoint matching offers **5** destinations from Amsterdam; the full stop chain offers **82**, Berlin and Prague among them — without which "Amsterdam → Berlin → Prague → Vienna" cannot be built at all. What the endpoints have that intermediate stops do not is a *time*, so `segmentOf()` reports a clock only for an end it actually knows. `build-plan-index` fills the gaps from operator feeds through `getStationTimesForTrain` (endpoint-validated, so a bare number two operators share cannot lend one train the other's clock): **249 legs, 4 054 stop clocks**. Where no feed carries the train, a mid-route boarding shows "departure not published" rather than a number interpolated between two endpoints.
- **Ranking is where a stopping pattern becomes a destination list.** Alphabetical put Amersfoort and Bad Schandau above Berlin and Prague from Amsterdam, and opened Paris with Assier, Aubin, Capdenac, Cransac and Gramat — five villages on the Rodez sleeper, above Rodez and Toulouse. Order is: what we can stand behind, then whether the ride crosses a night (Amsterdam → Amersfoort is a real call of a real sleeper and it is 36 minutes long), then whether the train **ends** there. That last test is `isTerminus`, deliberately **not** `isWholeRoute`: ES 453 runs Brussels → Prague, so from Amsterdam the ride is not the whole route while Prague is still the destination, and ranking on `isWholeRoute` filed it with the villages it passes at 3am.
- **A journey only changes trains where trains start or end.** `terminusCount` per city (set by the index build) gates the breadth-first walk, or Amsterdam → Vienna comes back routed via Bad Schandau and Děčín — two village stops on the through train it should have offered directly. Each hop is judged on **its own** night, not on the departure date repeated. A hop with no train is reported as a hop with no train: the plan stays on screen and says where it breaks, because "no results" for a four-city trip hides which of the three legs was the problem. And a plan's summary counts sleeper nights separately (`3 nights · 2 on a sleeper`) — Berlin → Prague at 18:13 arriving 22:16 is a four-hour evening ride, and calling it "Night 2" promises a bed it does not have.
- **A night train calls at places thirty minutes down the line, and those are not sleeper journeys.** Amsterdam → Utrecht is 26 minutes, Vienna → Wiener Neustadt 36, Brussels → Bruxelles 7; **39% of the segments whose duration we know run under four hours**. `MIN_TRIP_MINUTES = 240` drops them from **discovery** — the "where could you go" list and the journey search, so a chain is never stitched from half-hour hops. A pair asked for **by name** is never filtered to nothing: European Sleeper really does run Brussels → Amsterdam in 3h09, and answering "no night train we know of" would be false, so `ridesBetween` returns the short rides with `onlyShortHops` set and the itinerary says what they are. An **unknown** duration is never hidden — 31% of segments have none, and silence about a train is not evidence against it.
- **Two endpoint clocks cannot express more than a day, so the longest trains read as the shortest.** `durationBetween` wraps once, which made **UZ 099 Kyiv → București, a 23-hour journey, read as thirteen minutes**, the Cardinal's 26h30 as 3h28, VIA's four-day Canadian as 65 minutes and the Doğu Express as 2h26 — and a naive under-4h filter would therefore have deleted the longest trains in the dataset while keeping the commuter hops it was written to remove. Two repairs, in order. **`trip.duration` is authoritative and can express more than a day**: Back-on-Track writes it as a spreadsheet time on the Lotus/Excel epoch (`1899-12-30T12:47` = 12h47m, a second day carrying the extra 24h — 17 trips are longer than a day), it agrees with the clocks within five minutes on **267 of 318** legs and differs by almost exactly 1 440 minutes on 15, and `segmentOf` prefers it for the whole-route ride. **A synthetic row has no trip at all** and its feed stop times carry no date, so for those no correct number exists anywhere in the data — what exists is proof the number is wrong: straight-line distance over stated time, against `MAX_PLAUSIBLE_KMH = 160` (sleepers average 60–90 km/h over the ground and the fastest legitimate leg in the payload implies 134; great-circle distance *understates* the track, so the real figure is higher still). Such a leg is `durationSuspect`: it **withholds** its duration rather than guessing one, is treated as overnight (a train that fast over that ground is certainly crossing a night, and with the figure withheld nothing else would say so), and is exempt from the short-hop filter. 37 legs are flagged; end-to-end rides genuinely under four hours fall from 30 to **7** — two ÖBB Feldkirch–Zurich connector legs and five Trenitalia Palermo–Messina portions, all real.

- **A change of trains is checked against both trains' clocks, not against "the next night".** A plan date is a train's *night* (the date it leaves its origin), not the date you board it: NJ 19947 calls at Innsbruck at 00:47, which on the night of the 7th is the morning of the 8th. The old journey search chained hops a fixed day apart, so it offered connections onto trains that had already left (arrive Vienna 09:39, onward on a train calling there at 05:39), read SE1's 32 hours as arriving the next morning, dead-ended on any onward train that did not run tomorrow — Paris had no way at all to Vienna, Prague or Warsaw — and offered detours like Brussels → Vienna → Lviv → Budapest beside the routes they are worse copies of. `src/lib/plan/timeline.mjs` places every stop on its day as an interval `[earliest, latest]` in minutes after the train's night (a published clock is exact; an unpublished one lies between its known neighbours; the trips table's duration outranks the end clock), and `connectionBetween` answers `ok` / `unconfirmed` / `missed` with `MIN_CHANGE_MINUTES` (30) between trains. `resolvePlan` now dates each hop from the previous train's own arrival day (`rideArrivalDate`, never less than +1, so ordinary plans and their URLs are unchanged) plus stopover nights, ranks a train that has left last and does not count it as serving the hop, and gives each hop `connection` and `after`. `findJourneys` is a label search: changes only at interchanges, up to `maxWaitNights` (2) nights' wait at a change (carried in the plan as stopover nights), `flexNights` for a first train leaving later (the page retries with 6 when nothing connects on the chosen night), `after` when it fills a gap in a longer plan, and a journey is dropped when one with fewer trains arrives no later. Each result is resolved exactly as its URL resolves, and `spliceJourney` puts it into a plan in place of a hop. The page shows the options as full cards (`JourneyOptions`: the fare as one large sum, every train, every change with its wait and any cross-town station change; on a phone the per-train lines and the change's station/clock detail are hidden, leaving route, sum, dates and the change), under a two-city plan and inline under any unserved hop of a longer one. Where no train runs a hop at all but a change does, the change **replaces** the empty "no night train" box rather than sitting under it (`changeOnly` on the page, `changesInstead` in the itinerary) — the box was the loudest thing on the page and said the opposite of the answer; the "To" picker no longer offers the city the hop leaves from, nor "From" the first destination. "To" (and "Then on to") lists first the cities a train reaches from that city without a change (`directDestinations`, the same rides the journey search starts from, so short hops are not "direct"), marks them **direct**, and prints nothing beside the rest: a train count answered a question about the destination, not about getting there. `rankCities(…, { preferred })` puts preferred cities first in the unprompted list and within typed matches, but an exact name still wins, and without `preferred` the ranking is unchanged; "From" keeps its train counts.
- **A night-train dataset is not a market, so suggestion is weighted and availability is not.** Ranked by raw connectivity the "start from" chips opened with **Lviv, Kyiv, Beijing, Shanghai and Chengdu** — six Ukrainian and five Chinese cities in the top 24, Paris 19th, Amsterdam/Brussels/Milan/Rome absent. Every one of those routes is real; none is what someone planning a European sleeper trip came to be offered first. `data/overrides/city-prominence.json` carries a per-country weight **with its reason written next to it** (UA 0.15 — Ukraine is at war and heading a leisure planner with "start from Kyiv" is the wrong default; CN/US/CA 0.1 — real data, wrong market). `src/lib/plan/prominence.mjs` applies it, and the boundary is the whole design: it reorders **discovery only** — the landing chips, the picker's default list, and ties between equally-good destinations — and **never filters**. Every de-emphasised city keeps its legs, stays on the map, keeps its `/connections` page, is returned in full by any plan that asks for it, and comes back first the moment its name is typed, because match quality outranks weighting inside `rankCities`. A missing or unknown country weighs **1**, never 0: the default is "suggest normally", and eight terminus cities (Helsinki, Inverness, Latour-de-Carol…) rely on it. `verify-plan` asserts both directions.
- **A list is ranked by the number it prints, or it reads as unranked.** The "start from" chips were sorted by `suggestionScore` and captioned with `terminusCount`, so the numbers went 36, 29, 24, 22, 20, 16, **10, 9, 12, 12, 5** — every one of them true, none of them the sort key, and the first report of it was that the list "appears to be in plain alphabetical order". It was not alphabetical; it was ranked by something the reader could not see, which is indistinguishable. `startCityScore` is now the count on the chip — `routeCount`, distinct routes calling at the city, which is what "the most night trains" claims — and `byStartCityScore` is the one comparator both `getTopStartCities` (the pre-rendered props) and the page use, so the server's list and the one the loaded index replaces it with cannot be sorted differently. `routeCount` is deliberately not `legCount`: a route's two directions are two legs and one train.
- **A weight cannot be interleaved with the number it damps.** Ukraine's 0.15 gives Lviv (43 trains) a score of 6.45, which sorts it between Milan's 7 and Amsterdam's 6 — so the chips would read 8, 7, 7, 7, **43**, 6, which is the unranked-looking list all over again. `byStartCityScore` therefore puts every de-emphasised city **behind** every suggested one rather than multiplying them into one order: both blocks descend on their own count, and the shown window is the undamped block. It is not a stronger de-emphasis — the city keeps its legs, its map dot, its page, and comes back first the moment its name is typed — it is the only de-emphasis compatible with printing a count.
- **Three products in one table, so the chips have tabs rather than a heavier thumb.** Beijing has 40 night trains against Vienna's 25, and neither belongs above the other because nobody shopping for one is shopping for the other. `src/lib/plan/regions.mjs` splits the 189 start cities into **Europe 136, Asia 37, North America 16** — zero unplaced — and the landing section carries a `Europe / Asia / North America` tablist (arrow keys, roving `tabIndex`, `aria-controls` onto the chip list). A tab makes Chengdu a loud Asian city where a weight made it a quiet European one, so `city-prominence.json` gained a **`scope`** per weight: `always` (UA, for the war) survives into a tab, `global` (CN/US/CA 0.1, GE/AM/AZ 0.4) applies only where every continent competes in one list — the city picker's default list and the journey tie-break, which still read the unscoped lookup. Damping *inside* a tab would break the descending numbers it exists to produce. `START_CITY_LIMIT` is **32**, as one exported constant rather than a literal at each call site: at 24 the cut landed one slot above **Amsterdam** and took Brussels, London, Stockholm and Sofia with it, so a list headed "the most night trains" offered Bohumín and Gdynia and not them; 32 ends Europe at six trains and stops short of the 4–5-train tail. One constant because the server pre-renders these chips and the client re-renders them from the loaded index — two literals is two lists, and the difference reads as the list changing length a second after paint. `getTopStartCities` returns **every** region's top, not the default one's, or a tab switched before the index lands would paint an empty list. Eight hubs resolve to no country at all (Feldkirch is Europe's 7th busiest by trains, Helsinki, Inverness, Latour-de-Carol…) because their station name is absent from Back-on-Track's stop table under the spelling their routes use, so `CITY_COUNTRY_OVERRIDES` supplies one at index-build time — without it they carry no flag and fall out of every tab, which is worse than either.
- **A city is measured by where its trains go, not by who terminates there.** Weighting the city alone made **Przemyśl the 6th suggestion, above Prague**: it has twenty terminating night trains and nineteen of them are Ukraine's. It is a Polish city and must not be weighted as a Ukrainian one — so `scoreCities` counts each leg for the prominence of the place it *reaches* (`reach`/`terminusReach`). Przemyśl drops to 15th on its own merits with `prominence: 1` intact, while Vienna and Paris, whose trains go everywhere, do not move. The score is `(terminusReach × 3 + reach) × prominence` — a terminus counts triple because trains *ending* there make it a destination, while one they pass through at 3am does not.
- **Every city was country-less, and nothing said so.** `normalizeStops()` trims a stop to id/name/lat/lon, so `stop.stop_country` is undefined on all 29 810 of them and the index's country map was empty from the first build — no flag in the picker, and nothing for the weighting to key on. The build reads the **raw** stop index instead, and two things there are load-bearing: `stop_name_romanized`, because Back-on-Track stores Ukrainian stations in Cyrillic (`Київ Пасажирський`) while every route spells them in Latin (`Kyiv Pasazhyrskyi`) — a `stop_name`-only index misses Ukraine entirely, which is exactly the set being ranked; and `OPERATOR_COUNTRY_FALLBACK`, because a synthetic operator's stations (Beijing, Amtrak's network) are not in that table at all. 0 → **1 957 of 2 072** cities, 181 of 189 terminus cities. `normalizeCountryCode` moved to a dependency-free `src/lib/countryCode.mjs` so the raw-node build can call it rather than restate it — and `seo/countries.js` must **import** as well as re-export it, since `export … from` creates no local binding and the file calls it itself.
- **A native date input will not shrink inside a grid item.** `input[type=date]` has a wide intrinsic width from its native control, and a grid/flex item defaults to `min-width: auto`, so it refuses to shrink and pushes the card past the viewport — which is what spilled on a phone. The guard is `min-w-0` down the whole chain (page grid item → field wrapper → input) plus `box-border`/`max-w-full`/`appearance-none`. Worth knowing before trusting a measurement here: **desktop Chromium's date control is narrower than iOS Safari's**, so the page measured 0 px overflow at 390 px while visibly spilling on the device, and no WebKit browser is installed to reproduce it. `tests/smoke.spec.js` asserts 0 px page overflow and the input inside its card at **320 px**, which is the check that would have caught it.

- **`min-width: auto` bit twice, and the second time the test watched it happen.** The date-field fix above left `<div className="grid gap-3">` holding the result cards, and a grid with no column template sizes its implicit column `auto` — which floors the track at the item's **min-content**, while a grid item defaults to `min-width: auto` and so cannot shrink below it. The ride cards came out **440 px wide inside a 288 px container**: +66 px past a 390 px phone, +136 px past a 320 px one, with the availability badge sliced off. Tailwind's `grid-cols-1` is `repeat(1, minmax(0, 1fr))`, and that `minmax(0, …)` is the whole fix. **The instructive half is why the existing test said 0 px.** It asked `documentElement.scrollWidth - clientWidth`, and this app scrolls an inner `h-dvh overflow-y-auto` div while `body` is `overflow-x: hidden` — so the document reports 0 however far the content runs. It also measured after `#plan-date` appeared, which is before any result has rendered, so the only thing on screen was the form. Two wrong questions, one confident pass. The replacement asks the blunt one — after the cards are on screen, does **any** element's right edge reach past the viewport — and asserts a card count beside it, since a blank page also overflows by nothing. Reverting `grid-cols-1` fails it with `article… reaches past the viewport, Received: 136`.
- **The dataset is a static asset, not an endpoint.** `scripts/build-plan-index.mjs` → `public/data/published/plan-index.json` (~440 KB, 94 KB gzip), rebuilt nightly after `canonicalize`. Answering anything needs the whole leg graph, so an endpoint would re-merge and re-project the payload per request for data that changes once a night; as a committed artifact `next.config.js`'s `/data/:path+` headers and `public/sw.js`'s stale-while-revalidate already cover it, and the page stays static so a shared link resolves with no serverless hop. Names and pricing records are interned (`src/lib/plan/index-codec.mjs`, `hydratePlanIndex` idempotent like `hydratePkpBundle`) — written out in full it is 881 KB of one-line JSON, which is a diff no reviewer can read. Disabled routes are stripped exactly as `/api/initial-data` strips them.
- **Prices have a live seam, not a stub.** No operator carries a `fromPrice` yet, but 21 declare a pricing *model*, so 452 legs render advice a traveller can act on today ("Book early" for a yield-managed sleeper). `resolvePricing()` (`src/lib/pricingResolve.mjs`) is the route-first precedence as one function, because `operatorPricing.js` imports its JSON without an import attribute and cannot load in raw node — two copies of "which price wins" is exactly the drift this repo keeps paying for, and `verify-plan` asserts the two agree. The figure takes the same slot the day a probe produces one.
- **Every plan URL is one static page, never an ISR route.** `/plan/:path+` is rewritten onto the prebuilt `/plan` (`next.config.js`), and a header sends `X-Robots-Tag: noindex, follow` for those URLs, since their pre-hydration `<head>` is the landing page's. It used to be `[[...slug]]` with `fallback: "blocking"` + `revalidate`, which rendered and wrote an ISR cache entry for every distinct city × date URL a visitor or crawler produced, and Vercel warned in October 2026 that the team had used 75% of Hobby's 200 000 ISR Writes. Exceeding that **pauses the project**, so the "no freemium limits we could hit" rule applies: the static page costs no function invocation and no cache write, whatever the URL. `verify-plan` fails if any page declares `revalidate` or a `true`/`blocking` fallback. The page renders the empty planner (as the server did) and reads the plan off `router.asPath` (`planPartsFromPath`) after mount. Reading the URL on the first client render produces a different tree than the server sent, and React discards and re-renders the whole page. The same class of fault, found the same way: `toLocaleDateString("en-GB", …)` returns `"Fri 18 Sept"` under Node's ICU and `"Fri, 18 Sept"` under Chromium's, so **one comma** was a whole-page hydration failure — invisible in dev, only in production SSR. Planner dates format from a fixed table (`src/lib/plan/format.mjs`); no `Intl` reaches SSR'd output.
- **22 via-only stations gained a `station-cities.json` entry** so the planner works in cities rather than in station spellings: "Wien Meidling" appears on **45 legs** and resolved to its own city, as did München Ost (25), Warszawa Centralna (20), Basel SBB, Praha-Libeň and Kraków Główny — which also read "Kraków" against the endpoint table's "Krakow". Only stations that are **never** an endpoint were added, so no live `/connections/` slug moves; `verify-plan` pins that rule. (This is why `verify-seo-urls`' missing-city sample is now "Hamburg Wilhelmsburg" — Hamburg Dammtor stopped being an example of an unmapped name.)
- **A choice made in the form shows its result, not the form again.** On a phone the heading and the form are the whole first screen, and picking "To" used to *clear* the field it was typed in (it only ever appended) while the trip rendered below the fold — the tap read as a reset. Now a plan of two or more cities folds the form into a one-line summary (`TripSummary`: the date and **Change**), "To" shows and replaces the **last** city when reopened, every form change scrolls `#plan-results` into view (`scrollTarget`, consumed in an effect once the result has rendered — the page scrolls an inner `h-dvh` div, so Next's own scroll-to-top does nothing), and extending the trip is an **Add another city** button *after* the itinerary. Two things for someone who knows where they are going: a hop with no train that night offers the next night one runs as one tap (`nextServedNight`; on the first hop it moves the trip, on a later one it adds nights in the city before it), and each ride on a night it could run has a **Book** button (`rideBookingLink`, `src/lib/plan/booking.mjs`) — `resolveRouteBooking` with the stations the traveller boards and leaves at, the seller's `agency_id` (carried on the leg as `agencyId`, since `operatorIds` reads `bot_agency_id` first) and the plan's night as `isoDate` for an operator whose link takes one. An operator's own corridor page (`routePages`) still wins, as on the connection page.
- **A journey's fare is one sum** (`journeyFare`, `src/lib/plan/journeyFare.mjs`; `FareSum` in `JourneyOptions.js`): "from €40 + €69.90 = €109.90", large, on each change option and under "Your trip" for a plan of two or more trains. It adds each hop's best ride's `pricing.fromPrice` in cents (40 + 69.9 must print €109.90). A train without a published fare is a "?" and leaves **no** total, since adding nothing for it understates the trip; fares in two currencies are not summed; any yield-managed fare makes the sum a floor ("from"). Options with a change are listed **cheapest total first** (`compareJourneyFares`, applied in `findJourneys` before its `limit`, so the cheapest is never cut): a journey with a total before one without, and where price says nothing the old order (soonest arrival, fewest changes) decides. A segment boarded mid-route quotes its train's fare, as `RideCard` already does.
- Covered by `npm run verify-plan` (62 checks) plus planner cases in `tests/smoke.spec.js`.

### Cheap night trains (`/cheap-night-trains`)

**The fare calendars, read across trains instead of one corridor at a time.** A connection page answers "which night is cheapest on this train"; a flexible traveller asks "which sleeper is cheap in the next few weeks, and when", and nothing answered it — European Sleeper's last-minute and flash deals (not in the operator's own fare finder) were spread over four corridor pages, and the cheapest night of ~70 calendars was only visible by opening each. Linked from the SEO nav and footer, the map header, every connection page with a calendar, and the sitemap (`daily`, lastmod = the payload's date, which is this page's real one). The site is served from **`https://pingwi.com`** (moved from `sleeper-train-map.pingwi.com`, Aug 2026). The origin is written in exactly one place, `src/lib/seo/site.js`; everything else builds URLs through `absoluteUrl()`.

| Path | Page |
| --- | --- |
| `/` | Interactive map + SSR'd indexable tour (top ~50 connections, country + operator hubs) |
| `/plan` | **The trip planner.** Landing page; `/plan/{city}[-to-{city}…]/{date}` is a saved plan (noindex) |
| `/connections` | Directory of every city pair — the hub-of-hubs |
| `/cheap-night-trains` | Every deal on sale, each priced train's cheapest night, and weekend picks |

- **Slugs are city names, not station names.** `cityForStation()` (`src/lib/seo/cities.mjs`) resolves a raw station to its city: `data/overrides/station-cities.json` first (English exonyms + qualifier strips — "Praha hl.n." → Prague, "Zemun" → Belgrade), then a generic fallback that strips parentheticals, bilingual `A / B` halves and station-type suffixes. Add an entry when a new endpoint's fallback guess is wrong; `verify-seo-urls` reports uncovered endpoints without failing.
- **The city rule's expensive failure is the one it never reported.** `stationsMissingCityOverride` only flagged a station whose name the fallback had *changed* — on the reasoning that an untouched name is already its own city. That is true of "Sofia" and false of every name carrying a qualifier the fallback does not know, which is the case that costs a page: the name is left alone and quietly becomes its own city. **"Hamburg Altona"** therefore gave five Nightjet routes URLs under `/connections/hamburg-altona-to-*` plus a `/night-trains/germany/from/hamburg-altona` hub, with `"Hamburg Harburg": "Hamburg"` sitting one line away in the table; **"Milano Certosa"** exiled European Sleeper's *running* Brussels–Milan train to `/connections/brussels-to-milano-certosa` while the canonical `/connections/brussels-to-milan` carried only the December preview row — 12 stops, **zero times**, a train that does not run until the 14th — next to `"Milano Centrale": "Milan"`. Neither was ever reported in months of runs; the reporter's whole output was one correctly-resolved `Bologna Centrale`. It now also reports a name the table assigns a city to *through a sibling sharing its first word*, which catches both. What no heuristic catches is a single-token name: **`Mitry-Claye`** really is its own commune, and only a human knows European Sleeper starts ES 475 there while Paris Gare du Nord is under works — which made route 238 the one route in the payload emitting **two** connection pages, `berlin-to-paris` and an orphan `berlin-to-mitry-claye` with identical content and no canonical pointing at it (`getPairMap` indexes a route under *every* direction's city pair, while `buildSummary`'s `pairSlug` names only the first). `verify-seo-urls` now fails on a route emitting more than one page, which is the shape rather than the three entries. Moving a slug costs redirects: the six retired URLs are hand-seeded in `redirects.json` (the same thing was done before for `dnipro-holovny-to-uzhhorod` and `feldkirch-bahnhof-to-zurich`), and `build-redirects` repointed the nine `/trains/` entries that aimed at them. The dangling-destination check had never met a non-`/connections/` destination and would have rejected the hub one: it now validates a hub's city segment against the slugs the payload produces, and `tests/seo-redirects.spec.js` fetches every non-connection destination for a real 200, because the country table and `MIN_ROUTES_PER_STATION` do not load in raw node.
- **A pair page's title and description are rolled out operator by operator, starting with European Sleeper.** `src/lib/seo/snippet.mjs` (from PR #88, which proposed it for all 240 pairs at once and never merged) builds two variants. `FACTS` puts the query entity first with one number in the title and opens the description with the train, its clock and how often it runs. On European Sleeper's corridors (2026-10-01):
  - before: `Night Trains Brussels to Prague — Times, Stops & Tickets | Pingwi`
  - after: `Brussels to Prague Night Train — 15h 27m, 3× a week | Pingwi`, described as `European Sleeper ES 453 leaves Brussels 19:22 and reaches Prague 11:00 — 15h 27m, 3× a week. Tickets from €40. Full timetable, 11 stops and where to book.`

  `CONTROL` is the old template **byte for byte**. `snippetVariantFor()` decides per page from its trains' operators (`FACTS_AGENCIES`, today `["ES", "SNCF", "FS"]`): **only the four European Sleeper corridors, SNCF's nine Intercités de Nuit corridors and Trenitalia's eleven Intercity Notte corridors render FACTS, and the other 235 render CONTROL** (SNCF joined in October 2026 — 0 clicks from ~1 000 baseline impressions across its nine pages, so, like ES, little to lose; Trenitalia the same month — 0 clicks from 272 baseline impressions on the seven of its pages that existed then, and it pays commission like ES). Four of Trenitalia's pages (Catania–Milan, Catania–Rome, Milan–Palermo, Palermo–Rome) are newer than the baseline — they became corridors of their own when the timetable moved to Trenitalia's GTFS — so the report sits them out, and `verify-seo-snippets` names them (`TREATED_SINCE_BASELINE`) rather than let any other treated page go missing from the readout. Its descriptions name a train by the number Trenitalia sells it under ("Trenitalia ICN 1963 leaves Milan 20:10 and reaches Palermo 16:55 — 20h 45m, nightly. Tickets from €65.9…"), never a through-car portion's file key. Widening the rollout is adding an operator id; reverting it is emptying the set. The visible opening paragraph is `intro` (the old prose), never the description, since "ES 453 leaves Brussels 19:22…" is a snippet and not a first sentence. What the formula refuses to say:
  - a cadence ("Every 2nd day");
  - a stated duration contradicting its own clocks by more than an hour;
  - a duration the ground disproves (`durationPlausibility.mjs`, the 160 km/h test `build-plan-index` now imports rather than restates);
  - a frequency the train's own label contradicts (`directionFrequency`): Back-on-Track labels SNCF's Albi portion "IC Nuit 3754 (Sun)" while its row says "2026: Daily", and the first SNCF preview printed "IC Nuit 3754 (Sun) … nightly". Two sources disagreeing about when a train runs is withheld, not arbitrated.

  The description deliberately does **not** carry SNCF's punctuality figure, though its pages have one: the AQST data runs about five months behind ("in May 2026" in an October snippet) and the live figures range from 52% to 100%, so it is read on the page and in the FAQ, with its month and 12-month figure, rather than in a snippet.

  Porting it found two more faults, both on European Sleeper pages:
  - **Equal clocks at both ends are a placeholder.** Amsterdam–Milan ES 454/455 ("Postponed to 2027") states 00:00 → 00:00, and the first cut printed "leaves Amsterdam 00:00 and reaches Milan 00:00 — 24h".
  - **A timetable opening more than two weeks after the build is not the one described** (`today`, `UPCOMING_AFTER_DAYS`). Brussels–Milan carries December's routing as its own row with one stop more, and was described with December's days. Two weeks rather than "after today", because a feed states a running train's window from its next run: ES 474 opened "2026/10/02" on 1 October.

  **Every page in the rollout ships in the sitemap, even in batch 1** (`inRollout` in `sitemap.xml.js`, reading `operatorIds` that `getAllCityPairs()` now carries and `/connections` strips from its props). Brussels–Prague, European Sleeper's main line, ranked 88th by batch 1's alphabetical tie-break among one-train corridors and was in no sitemap at all: 9 impressions at position 43.9 in the baseline quarter. The first cut of that read `pair.routes`, which `getAllCityPairs()` does not carry, and the sitemap's own try/catch dropped **every** data-derived URL — 67 URLs and no connection pages, served with a 200 — which is why the check is a live `next start` read of `/sitemap.xml` (148 URLs, 81 connections) and not the build passing.

  **The other pages are the control group.** `data/seo/snippet-baseline.json` is a real Search Console export for every pair (2026-06-21 → 2026-09-20, before any snippet change). `npm run seo-snippet-report <export.csv>` reads the treated pages' CTR and position change net of the untreated pages', which share the site's drift. **A control page that gained a price is not a control**: no published page carried a fare before the baseline closed (the first nightly official fare, 12306's, landed 2026-09-26), and a page that gained a "From" tile, a price question, a price in its description and often a fare calendar changed more than its wording — so the report reads those apart as a third row, `priced`, and leaves them out of the net figure. In October 2026 that is 63 pages (12306, Intercity Notte and ÖBB's Nightjet corridors) holding about half the control group's baseline impressions; `published-pairs` carries `priceSources` so the report can say whose. Covered by `npm run verify-seo-snippets`:
  - the gate selects exactly the European Sleeper corridors, and every other page is byte-identical to the old template;
  - placeholder clocks and the December preview are refused;
  - FACTS fits the title and description budgets on **every** pair, so widening the rollout has nothing left to discover;
  - the report reads its own baseline as 1.00× on both arms.

- **Pairs are undirected.** `buildPairSlug()` sorts the two city slugs, so both directions land on one page instead of two near-duplicates. Ordering helpers live in `src/lib/seo/slugify.mjs` (`.mjs` so raw-node scripts and the Next build compute identical slugs — divergence would emit redirects to URLs the build never renders).
- **The SEO layer sees what the map sees.** `/api/initial-data` withholds admin-disabled routes via `stripDisabledRoutes`; `src/lib/seo/data.js` reads the published artifact directly and so used to keep serving them — which left Back-on-Track's retired European Sleeper *456/457* (Brussels–Milan **via Zürich**, route 240) with a live connection page after the operator's own feed replaced it with ES 400/401 via Aarau. `getPublished()` now applies the same strip, and `scripts/build-seo-redirects.mjs` applies it too before computing targets.
- **`/trains/{slug}` is retired.** Those pages 301 into their `/connections/` parent. `data/seo/redirects.json` holds the map, regenerated by `npm run build-redirects` (nightly, after `canonicalize`) and **append-only on the source side** — a route can vanish from the dataset but its indexed URL must still resolve. A *destination* is not a promise, though: the route behind a page can vanish or be disabled, and a 301 into a 404 is worse than no redirect, so every destination is checked against the pages the payload actually emits and a dead one is repointed (same pair under the other slug order when that exists, else `/connections`). `next.config.js` turns it into 301s, listed *before* the legacy-host catch-all and with absolute destinations in production so a request to the old host resolves host **and** path in one hop.
- **The old host stays attached to the same Vercel project.** Do NOT configure a Vercel domain-level redirect for it — that preserves the path and forces a second hop through the retired URL.
- **`lastmod` is per-URL, and it is not the payload's date.** Every sitemap URL used to carry the published artifact's `generatedAt`, so each nightly scrape told crawlers all 144 submitted pages had just changed — on a site Google samples at ~25 crawls/month that spends the entire budget re-reading routes untouched since June, and an always-"now" lastmod is a signal a crawler learns to discount. `route-history.json` already dates each route's last real change and only the integrations dashboard read it; `buildSummary()` now stamps `lastChanged` on every route summary, each hub aggregate takes the max over its routes (`lastChangedOf()`), and `lastmodFor()` (`src/lib/seo/lastmod.mjs`) answers per URL — 16 distinct dates against the committed history instead of 1. `CONTENT_VERSION_DATE` is the floor and the subtle part: a route's own date is right for a **data** change but not for a **template** change, which moves every page at once, so it is bumped **by hand** when the page templates change materially and is deliberately *not* the deploy date — that would put "changed today" back on every URL and undo the whole thing. A malformed `lastChanged` falls back rather than reaching the sitemap, and `verify-seo-urls` fails on a future lastmod (crawlers discard a sitemap that claims one) and on the history collapsing to a single date.
- **Sitemap indexation is staged.** `SITEMAP_BATCH` in `src/pages/sitemap.xml.js`: `1` ships ~145 URLs (core + hubs + top 80 connections), `2` ships everything. Flip once GSC shows batch 1 indexing. The sitemap must only ever contain canonical, indexable, 200-returning URLs — `tests/seo-redirects.spec.js` asserts it lists nothing that redirects.

### Key Architectural Decisions

- **No Vercel paid features. No freemium features with usage limits we could hit.** Stick to OSS Next.js features and the Vercel Hobby tier surface area. That rules out Vercel Blob, KV, Postgres, Edge Config, Vercel Cron (use GitHub Actions instead), and any `maxDuration > 10s` config in `vercel.json` (Hobby caps Serverless Functions at 10s). When adding a feature that would normally lean on a managed Vercel service, commit the data to the repo and serve it from `public/` or bundle it via an ESM import.
- **Bundled data files vs. `public/` static assets:** JSON in `data/` that API routes need is *bundled into the lambda* via ESM JSON imports (`import ... with { type: "json" }` — see `primitives.mjs`, `build-initial-data.mjs`, `initial-data.js`). Never `fs.readFileSync` something from `data/` in an API route — Next.js doesn't trace dynamic file reads and the file won't be in the Vercel bundle. Larger nightly artifacts live under `public/` so the daily-scrape commit ships them as static assets and the lambda reads them from disk. (Scripts under `scripts/` run in raw Node and may fs-read anything.)
- **Every serverless route pays for the data it can reach, once per deployment.** Vercel's Deployment Storage bills the build output plus one function bundle per route, for every deployment it retains — and the nightly scrape commits to main, so the project mints a deployment a day and pays that bill again each night. `file-store.mjs` reads its datasets as `fs.readFileSync(path.join(DIR, name))`, a literal directory and a runtime argument; `@vercel/nft` resolves the directory, cannot resolve the argument, and conservatively traces **the whole directory in**. It is reachable from nearly every API route, so all ~24 MB under `public/data/` landed in all ~15 lambdas: **370 MB of function bundles per deployment**, which filled the 10 GB free tier in about three weeks. `/api/osm-relation` carried 24.6 MB to run 0.5 MB of code, and `/api/admin/*` — loopback-only, hard-404 on Vercel — carried the full set to answer 404. The `outputFileTracingExcludes` table in `next.config.js` states per route what it cannot reach. Two things to know before editing it. **Excludes are applied after includes** (`next/dist/build/collect-build-traces.js`: `new Set([...traceContent.files, ...includes])`, *then* the exclude filter), so a blanket `'*': ['./public/data/**']` silently deletes the per-route `outputFileTracingIncludes` beside it — excludes must be per route, which is why the table enumerates them. And the route keys are matched with picomatch `contains`, so a key is a substring test, not an exact one: `'/api/admin'` covers all four admin routes, while spelling out `'/api/admin/proposals/[id]'` would match nothing, since `[id]` reads as a character class rather than as a literal path segment. A new API route inherits **everything** until it gets a row — adding one without a row is how this silently grows back. **The other multiplier is how many deployments are retained, and on Hobby that is mostly branches**: Vercel keeps the latest deployment of every live branch whatever its age, so each merged `claude/*` branch left on GitHub holds a whole deployment (static `public/` included, ~30 MB of which no browser fetches). In October 2026 the repo had 88 branches against ~18 open PRs, which put the team at 75% again after the tracing fix — so delete head branches on merge (GitHub → Settings → General → *Automatically delete head branches*), and keep an alias as a rewrite rather than a page file (`verify-bundle-tracing` checks both halves of that). A related trap sits one level up: any `.js` file under `src/pages/api/` becomes a *route*, so the helpers in `api/lib/` are `.mjs` deliberately. As `.js` they were four extra 24.6 MB lambdas on publicly reachable URLs, two of them (`train-fetcher`, `cd-fetcher`) with no importer anywhere in the repo.
- **CDN requests are a quota too, and link prefetching spent it.** Vercel Hobby includes 1M CDN requests a month and the site used all of them in October 2026. In production a Pages Router `<Link>` prefetches its target's page data (`/_next/data/<build>/….json`) and route chunk the moment it scrolls into view, and the SEO pages are lists of links: one homepage visit made **118** requests to Vercel, 57 of them prefetches of pages nobody opened, and `/connections` made 114 (72). `src/components/Link.js` is `next/link` with `prefetch={false}` by default — Next still prefetches on hover, so the page about to be opened is warm — and with it the same visits make 41 and 14 (`/connections/brussels-to-prague` 57 → 24, a country hub 66 → 17, `/plan` 48 → 18). Import it instead of `next/link`; `npm run verify-cdn-requests` fails on a direct import or a `router.prefetch()` call. The service worker is the other half: its stale-while-revalidate refreshed every data file in the background on every visit, so a reload cost as many requests as a first visit; `needsNoRefresh` skips that refresh while the cached copy is under an hour old (`REVALIDATE_AFTER_MS`, the API's own `s-maxage`). What is left per page is mostly the page's own JS chunks (cached immutably after the first visit) and the two `/_vercel` scripts that `@vercel/analytics` and `@vercel/speed-insights` load, which are themselves freemium products with their own monthly caps.
- **AI is free-tier and never load-bearing.** `scripts/lib/ai.mjs` calls GitHub Models with the Actions `GITHUB_TOKEN` (`models: read`), hard request budget + spacing, returns null on any failure; all AI steps are `continue-on-error` and only ever produce proposals.
- **The first paint has a payload budget, and it is not the dataset's size.** `/api/initial-data` used to be 1.4 MB gzip and the client `Promise.all`'d it with the 1.1 MB PKP bundle, so nothing at all drew until ~2.5 MB had landed — about 17 s on 3G. It is now ~120 KB, because `src/pages/api/lib/payload-projection.mjs` serves only what the map renders, the same way `stripDisabledRoutes` already narrowed the published artifact at serve time (the artifact itself stays complete, so `verify-build-parity`, canonicalize and the SEO layer are untouched). Three projections, each removing something no component could reach: **stops** shipped all 29 771 Back-on-Track stations when `useMapMarkers` only renders one that a route names — it drops any stop with no `cities[]` entry — so ~94% were downloaded, coordinate-enriched and filtered away; **trips** carried five columns from the upstream spreadsheet export (`Merged Doc URL - ONTD_Chatbase_Export` and friends, plus an empty-named `#N/A` column); and **geometry** is 1.05 MB the default first paint does not draw at all, since `showRoutes` starts `false`. Two subtleties the tests pin down: the stops keep-set is unioned with `getGtfsBundleStationNames()`, because `attachPkpGtfsPolylinesToViewMap` rewrites `via_0` from the GTFS bundle's own stop list *after* the payload is built and expects those coordinates to be there already (without it five Berlin–Warszawa corridor stops lose their markers); and stops are matched on `stop_id` **and** `stop_name`, because 703 records spell the two differently (the bilingual Belgian names, `"Mons / Bergen"` vs `"Mons"`). The knock-on effect is that station search now covers sleeper stations rather than every station in the dataset — consistent with `NearbyStationsSheet`, which already filtered that way. Covered by `npm run verify-payload-projection`, whose central assertion is the inverse of the size one: every station the renderer could have drawn must survive, since a station dropped here just silently never gets a marker.
- **A request fired twice is a request the user pays for twice.** Every place the map fetches something has to answer "what if this effect runs again before the first response lands", because the naive guard — "have I already got it?" — never catches a request still in flight. `useInitialData`'s module cache holds the in-flight *promises*, not just results (React strict mode's double mount). `useRoutePaths` keeps `requestedPolylineKeysRef`, because its fetch effect depends on `osmPolylines` and each resolved fetch re-runs it: the 872 KB gzip of static polylines and OSM relations were being pulled roughly twice over, and a failed key is deleted from the ref so a later run may still retry. And `TrainDetailPanel`'s `useRoutes`/`useTrips` take `enabled` — they are fallbacks for rendering the panel without the map's data, but `DynamicMap` always passes `viewMapData`/`tripsData`, so `viewMapData || fetchedRoutes` discarded 146 KB gzip on every page load.
- **Caching is where a repeat visit gets its speed, and `public/sw.js` decides it.** Data payloads (`/api/initial-data`, `/api/route-geometry`, `/api/osm-relation`, `/api/trains`, everything under `/data/`) are served **stale-while-revalidate** against a 24h ceiling: the scrape commits once a night, so a copy from this cycle is as good as a fresh fetch, and the ceiling bounds how long a visitor can sit on an older *shape* of a file after a deploy that changes one (`hydratePkpBundle` being idempotent is the other half of that safety). `isNeverCache` matches the loopback-only admin page as `p === "/data"` and **not** as a prefix — as a prefix it also excluded `/data/gtfs/pkpTrainShapes.json`, so the largest asset the map downloads was the one thing never cached, which nothing short of watching the network panel would reveal. `next.config.js` `headers()` gives `/data/:path+` real cache lifetimes (Vercel serves `public/` with `must-revalidate`, a round trip per file per load); `:path+` rather than `:path*` so it cannot match `/data` itself. Covered by `npm run verify-service-worker`, which evaluates the shipped file in a `node:vm` context.
- **Tiles are the one cost that scales with how much the user moves the map**, and `tileLoadingOptions.js` keeps them off the wire: single-origin `tile.openstreetmap.org` (the `{s}` subdomains are deprecated, and on HTTP/2 three hostnames mean three TLS handshakes instead of one multiplexed connection), `updateWhenZooming: false` and `keepBuffer: 1` always, and `updateWhenIdle` only when Leaflet already wants it (mobile) or the Network Information API reports `saveData`/2g — forcing it on desktop makes a fast connection feel worse. The interactive map was also missing the OSM attribution the tile usage policy requires; only the SEO route maps carried it.
- **Map is always client-side only** — never attempt SSR for anything in `src/components/Map/`.
- **The dark map is OpenStreetMap's own tiles under a CSS filter, not a dark tile service.** Every dark basemap provider (CARTO, Stadia, MapTiler) is a freemium API with a view cap, which the rule above rules out. The visitor picks Auto / Light / Dark in the map settings (`useMapTheme`, stored as `train-map:mapTheme`, "Auto" following `prefers-color-scheme` live), and the map page writes the result to `<html data-theme>` — removed on unmount, since the SEO pages are dark by design and must not inherit it. Tailwind's `dark:` variant is redefined in `globals.css` to key on that attribute, so `dark:` classes do nothing anywhere else. The filter targets only `.basemap-tiles` (the base `TileLayer`'s static `className`; Leaflet reads it once, which is why the theme flips through the attribute rather than by re-creating the layer) — the OpenRailwayMap overlay colour-codes track types and stays unfiltered. A third of the operator palette is navy or midnight blue and vanishes on the dark land, so `liftForDarkMap()` (`src/lib/mapTheme.mjs`) raises a colour's HSL lightness, same hue, until its relative luminance clears 0.16 (≈3.4:1 against the filtered land, WCAG's 3:1 for graphics); a colour already bright enough (ES, VIA, ÖBB) is returned unchanged. It is applied wherever an operator colour is drawn or printed — the line, the bottom-bar chip's stripe, the panel's train chip and pricing badge. Station dots draw their ring as `var(--station-ring, white)` (`mapIcons.js`, the grouped icon in `useMapMarkers.js`), which the dark theme sets to the map's own dark: a white ring glares there, while a dark one still parts a dot from the line through it. The light theme is pixel-identical to before. Covered by `npm run verify-map-theme`.
- **Where an operator sells a corridor on its own page, that page is the booking CTA.** `routePages[routeId]` is the top booking tier (`LINK_TIERS` in `operatorAgencies.mjs`), above the station-preselect deep link: for European Sleeper's Brussels–Prague the operator's own corridor page beats a prefilled search into the booking engine, and it carries the same affiliate redirect as every other ES link (`deals.europeansleeper.eu/c?…&u=` takes a path, as the existing `dealsUrl` does). It is the same key `naBooking.mjs` reads for Amtrak/VIA, which resolve through their own builder and so never hit this tier twice. A route with no curated page keeps the deep link, and omitting `routeId` resolves exactly as before the tier existed. Because a route page does not preselect, `resolveRouteBooking` reports `preselects: false` and the caller drops the "Preselects X → Y" caption. The timetable link is unaffected and stays one page per operator for ES — corridor pages are for selling, `europeansleeper.eu/timetable` is what the operator stands behind for times (and what `es-timetable.mjs` parses).
- **The booking CTA answers "where do I buy"; the "Official timetable" link answers "where do I check".** They are different questions with different winners, so they resolve separately. Booking tiers components of a compound agency id by *link quality* (who sells the ticket); the schedule link tiers by *specificity* — for `CFM/CFR` a per-train CFR page beats CFM's homepage — and it follows `bot_agency_id` (who **operates** the train) rather than the selling agency. Five tiers, most specific first (`SCHEDULE_TIERS` in `src/lib/operatorBooking.js`): `scheduleTrainPages[number]` → `schedulePages[routeId]` (VIA Rail, SJ Nord) → `scheduleUrlTemplate` with `{train}`/`{date}` → `scheduleCountryPages[cc]` → flat `scheduleUrl`; nothing configured means **no link**, never a homepage that answers nothing. It renders as a muted text link under the station list on both surfaces — `TrainDetailPanel` (per trip card) and `RouteTimetable` (per direction) — deliberately not a second CTA. `resolveScheduleLink()` in `operatorAgencies.mjs` is the single entry point. Covered by `npm run verify-schedule-links`.
- **A route is not a train, so the most specific tier is keyed by number.** `schedulePages[routeId]` was the top tier, and a route id is the wrong key for an operator whose timetable page addresses one direction: Ukrainian Railways' Kyiv–Bucharești runs as **099** southbound and **100** northbound, with a separate `?ntrain=` page each (`105997` and `106002` — UZ's own internal ids, which are not the train number and cannot be derived from it). A route-keyed entry can hold only one of the two, so one direction would link to the other's timetable. `scheduleTrainPages` sits **above** `schedulePages` and is keyed by `scheduleTrainNumber(train)`, the same normalisation the `{train}` template uses — so the row's `"099"` resolves to `"99"` and a suffixed label like `"029 K"` would resolve to `"29"`, and a row whose number is absent falls straight through to the route tier it used to occupy. The tier is per operator like every other, so UZ's other 22 routes keep the `train` tier's generic search URL. `SCHEDULE_KEYS` in `overrides-mutate.mjs` carries the new lookup through an admin booking-URL edit, which rebuilds the record from a whitelist and would otherwise drop it silently — the same trap `affiliateWrapper` fell into.
- **A schedule link is per-direction, and its number is not the panel's lookup key.** `scheduleTrainNumber()` takes the first run of digits and drops leading zeros, because that is how the operators address their own trains: Ukrainian Railways writes train `001 D` as `1` and `036 Š` as `36`, and Back-on-Track's compound labels (`IRN 1954/R 8824`, `IRN / IC 78`, `1003 (G)`) carry the leg we link to first. It is deliberately **not** `extractTrainNumberDigits()` in `TrainDetailPanel`, which matches `/\d{3,5}/` — that one is a lookup key into the feed maps, so it must keep returning `"001"` verbatim and must keep missing two-digit numbers; changing it would break the ČD/GTFS timetable matching. UZ also numbers the two directions separately (35 Przemyśl→Odesa, 36 the other way) where BoT records one number plus a suffix letter, so ~23 UZ routes link one direction to its counterpart's number — the right train either way.
- **Per-country schedule pages need endpoint countries the payload used to drop.** Nightjet slugs its destination pages by German country name (`/en/reiseziele/niederlande`), but `normalizeStops()` trims stops to id/name/lat/lon, so the client had no country at all. `stampEndpointCountries()` in `build-initial-data.mjs` writes `origin_country_{dir}`/`destination_country_{dir}` onto each viewMap row from the raw Back-on-Track stop index — two ISO-2 codes a direction instead of shipping `stop_country` for all ~29k stops (155 of 286 rows; synthetic operators' stations are absent from that index and do not need it). `pickScheduleCountry()` then prefers the **destination**, falling back to the origin when the destination is the operator's own `homeCountry` — so Zürich→Amsterdam lands on the Netherlands page and Bruxelles→Wien on Belgium's rather than Austria's. Nightjet transliterates umlauts in the path rather than carrying them (Österreich → `/reiseziele/oesterreich`), which the operator confirmed; a country with no curated page still falls through to the destinations index rather than guess a slug. Romania needs none: its one route is jointly `CFR/MÁV/ÖBB` and CFR takes it at the per-train tier, above the country one.
- **Some operators address a train by station code and departure day, not by name.** Trenitalia's per-train page is `cercaTreno.jsp?treno=1962&origine=S12349&datapartenza=1788818400000`: `origine` is Viaggiatreno's own id for the origin station (S12349 = Siracusa) and is not derivable from the station name, and `datapartenza` is **midnight of the railway day in the operator's zone** — UTC midnight would point at the previous day's train for the two hours either side of it. So `scheduleUrlTemplate` also takes `{originCode}` and `{dateMs}`, the latter resolved through `scheduleTimeZone` (`localMidnightMs()`, derived from `Intl` so DST and sub-second drift are handled — the instant is floored to the second first, or the current time's milliseconds leak into a timestamp that must land exactly on midnight). A template only fires when **every** placeholder it names is fillable; otherwise the link falls back a tier rather than opening a search for nothing. The codes ride with the data instead of being hand-maintained: `scripts/adapters/trenitalia-gtfs.mjs` writes each stop's `stations[].code` (the GTFS stop_id is Viaggiatreno's code without the S), and `stampScheduleOriginCodes()` in `build-initial-data.mjs` writes `schedule_origin_code_{dir}` onto each row from that direction's own train — ICN 1962 leaves Siracusa, ICN 1963 leaves Milano Centrale. The Back-on-Track FS rows ("IC Notte 752") carried no code and stayed on the Intercity Notte page; since the GTFS covers every ICN number, none is left. **The stamp is per source, in that source's own agency scope** — the bare-number collision again, met here for the fourth time. Flattening every source's trains into one map keyed by number put Entur's quay id for Trondheim S (`NSR:Quay:1080`) onto European Sleeper's ES 475 row the day Norway was added, because SJ Nord runs a 475 too. It rendered nothing wrong only because no Vy/SJ Nord `scheduleUrlTemplate` names `{originCode}`, which is the worst shape a fault can have: correct-looking until someone adds one. Scope comes from `enrich.agencyIds` ?? `synthetic.botMatchAgencies`; absent still means "any row", which stays right for route-name keys like Amtrak's. Covered by `npm run verify-schedule-links`.
- **Some operators publish the timetable as a PDF, and the link has to say so.** All four Norwegian night routes do — Vy's Bergensbanen (605/606), SJ Nord's Dovre (405/406) and Nordland (475/476), Go-Ahead's Sørtoget (F5 725/726) — so they sit at the `schedulePages[routeId]` tier, one PDF per line. Go-Ahead had **no** timetable link at all before, since no operator page was ever confirmed for it and the rule is "nothing configured means no link"; SJ Nord's two moved off the `/strekning/` landing pages onto the timetables those pages link to. An unlabelled link to a PDF starts a download instead of opening a page, which is a worse surprise on a phone than anywhere else, so `getScheduleLabel()` takes the **resolved url** and appends "(PDF)". Reading the url rather than a per-operator flag is the load-bearing part: Vy's route-tier link for 605 is a PDF while its operator-tier fallback (`vy.no/en/traffic/times`) is an ordinary page, so one label on the operator would have to be wrong about one of the two. The match is anchored on the extension (`.pdf` with an optional query or fragment), so a path merely containing "pdf" is not claimed. **The cost to know about: two of these URLs carry their timetable period in the path** (`/2025/12/the-dovre-line.pdf`, `/2026/02/the-nordland-line.pdf`), so the December change will publish new files at new addresses and these will go stale — and a stale timetable presented as official is the exact failure the SNCF work above exists to prevent. They need re-checking at each timetable change; the landing pages they replaced are `https://www.sj.no/en/strekning/dovrebanen-2/` and `.../nordlandsbanen/` if a link that ages well is ever wanted instead. Covered by `npm run verify-schedule-links`.
- **Outbound schedule links can carry affiliate tracking.** `affiliateWrapper` is a per-operator template with a `{target}` placeholder, substituted URL-encoded — the Effiliation shape SNCF's booking link already uses. Set it and the link is wrapped and marked `rel="sponsored nofollow"`; absent, the link goes straight to the operator. Wrapping is idempotent — a value that already starts with the redirect is left alone, which is what lets European Sleeper store its links pre-wrapped (its `u=` takes a site-relative path, `%2Ftimetable`, which no longer exists once the value is a full URL) while still declaring the wrapper so **every** ES link is marked affiliate and any plain URL added later is wrapped automatically. `SCHEDULE_KEYS` in `overrides-mutate.mjs` carries all of this through an admin booking-URL edit, which rebuilds the record from a whitelist and would otherwise drop it silently.
- **A train no feed claims still has a stop list.** `TrainDetailPanel` picks a schedule by looking the train number up in one of **nine** per-operator feeds (`gtfs`, `nightjet`, `cd`, `chinese`, `italian`, `caucasus`, `curated`, `na`, `es`) — a hardcoded chain, and the one place the "no hardcoded operators" rule does not hold. A train none of them carries therefore showed **no stop list at all** in the panel, while the connection page for that same row showed one, because `src/lib/seo/data.js` falls back to `[origin, ...via, destination]`. That asymmetry covered every Back-on-Track-only route — all four Norwegian night trains, SNCF's Intercités de Nuit, CFR, and the long tail. `viaScheduleForTrip()` (`src/lib/viaSchedule.mjs`) is that fallback as one shared function so the two surfaces cannot disagree, wired in **last** so a feed that does know the train always wins. Times are only ever the row's own endpoint times: a via name carries none, and inventing one is worse than a blank. It also improves by itself — an enrichment that rewrites `via_*` from official data (SNCF, Entur) lands in the panel through it without the panel learning a tenth feed. Covered by `npm run verify-via-schedule`, which also asserts the chain order in the panel source, since the whole bug was ordering.
- **A row names the trains file that times it, so the panel does not need an eleventh feed.** `build-initial-data` stamps `timetable_source` on every synthetic row (the registry source that built it) and on every Back-on-Track row an official source corroborated through `trainsByNumber` (a bundle source like `pkp-gtfs` has no trains file and is skipped — its times reach the panel through `pkp_schedule_*`). `TrainDetailPanel` reads `/api/operator-trains?source=<timetable_source>` for any trip none of its per-operator feeds claims (`isKnownFeedTrip`) and looks the train up by the row's own label — safe from the bare-number collision because the file is the one that row was built from. `sourceFeedSchedule()` (`src/lib/sourceFeedSchedule.mjs`, dependency-free) turns it into the panel's schedule shape, and it sits **below every per-operator feed and above `viaSchedule`**. Two faults it closes: Trafiklab's new Stockholm–Luleå row (`trafiklab_93`), like every `cfr_` synthetic row, showed "No Back on Track trip data for this selection", because `fallbackTrips` only admitted trains a hardcoded feed recognised; and a corroborated row's card listed its official stops with a time only at each end while the feed that corroborated it times every one (SJ 91: 13 stops, 11 of them untimed). A failed fetch warns only where a synthetic row depends on it. Covered by `npm run verify-trafiklab`.
- **Enrichment corrects the row and never the trip, so a surface reading the trip renders the timetable the operator replaced.** The trips table is the upstream Back-on-Track export and nothing in the pipeline writes to it; the *row* is what `enrich-view-map.mjs` fixes. `TrainDetailPanel` renders trip cards, so it fell through to `trip.origin_departure_time` / `trip.via` / `trip.duration` / `trip.service_id` and showed all four stale — while the map line, the bottom bar and the connection page, which read the row, showed the corrected values. The same route disagreed with itself depending on where you looked. Across the published payload: **18 directions where the trip card contradicts its own row on a time, worst 183 minutes** (IC Nuit 3750, Back-on-Track's 19:44 against the SNCF export's 22:47), and **52 directions where the trip's via list is 2–5 stops against the row's 6–16**. It is not an SNCF problem — three of the worst eight are European Sleeper, 62–76 minutes out — it is every source that enriches. Duration was the loudest, since both numbers print in the same card: IC Nuit 5789 read "Duration 11h30" directly under its own "20:57 → 08:24". `officialRowSchedule()` (`src/lib/officialRowSchedule.mjs`, dependency-free `.mjs`) answers with the row's half of the record, and only for a row carrying `official_sources` — which means exactly the right thing, since enrichment stamps only a row whose feed trip it actually took (`takesFeedTrip`), so the two refused Paris–Aurillac stubs are unstamped and keep Back-on-Track's everything. Duration is **measured** from the row's two endpoint times rather than read, wrapping past midnight, which is what `routeDurationMinutes()` in `seo/format.js` already does for the connection pages — this is that rule for the rest of the record, shared so the two surfaces cannot disagree about one train (the reason `viaScheduleForTrip` is shared too). It slots **below every per-operator feed and above `trip.*`**: a feed that knows the train first-hand still wins, and where one exists it is usually what stamped the row anyway. It carries the row's **endpoints** too, for the card's "Route" header: a source with `updateEndpoints` moves where a train starts (Trafiklab runs SJ 91 from Umeå, Back-on-Track's trip says Luleå), and a header read from the trip sat above the other city's times and stops. Covered by `npm run verify-official-row`, which pins the precedence against the panel's source — the defect is ordering, and the component's extensionless imports will not load in raw node, the same reason `verify-via-schedule` asserts its chain order — and pins the payload measurements beside it, so a reverted tier fails against the numbers that justify it.
- **The bottom bar names a train from where the traveller is, in the order the business wants.** Three rules, each in a dependency-free module the bar calls. **Order** (`orderByPromotion`, `src/lib/operatorPromotion.mjs`): trains that do not run yet go **last** — never opened (`hasUnknownStart`, e.g. ES Amsterdam–Milano "Postponed to 2027") or the next timetable's preview row (`draw_as_active` + `routeHasNotStartedYet`), shown muted with "not running yet" — and among the rest, operators ranked in `data/overrides/operator-promotion.json` lead: European Sleeper (`ES`, rank 1), then Trenitalia (`FS`, rank 2), both of whom pay commission. It is kept as data with its reason beside each entry, a stable sort (nothing else moves), and a route counts if **any** operator in `agency_id` or `bot_agency_id` is promoted. It runs **before** the bar's origin–destination dedup, so on a shared corridor the promoted operator's route is the one kept. **Name** (`stationFirstEndpoints`, `src/lib/stationFirst.mjs`): a row states its endpoints in one fixed direction, so a click on Milan used to list "Bruxelles Midi – Milano", the train you board in Brussels. The chip now starts at the selected city's own station; at an intermediate stop it names the **farther** endpoint by great-circle distance (the longer night on the train — ES 453 from Brussels reads "– Berlin", not "– Paris"), falling back to stops-left when a coordinate is missing. Both directions' stop lists are searched, because they can differ (ICN 796 runs Salerno–Torino along the coast, its return 797 inland through Milano). **A one-way row is never pointed against its only train**: 45 of 298 rows state one direction (ICN 752 Lecce→Milano, ICN 1963 Milano→Siracusa as separate rows), so from mid-route they point to their terminus, and at the terminus they keep their real direction ("Lecce – Milano Centrale") rather than invent a departure — the rule that caught "Bologna – Lecce" for a train that only runs to Milan. Two chips that would read identically get their train numbers (`disambiguateLabels`: ICN 752 / ICN 1962 from Bologna to Milano). **Width**: a chip is capped at `calc(100vw - 1rem)` and its destination truncates, so no chip runs off a phone. **The "more to the right" fade must not scroll**: it used to be a `::after` on the `overflow-x-scroll` element itself, and absolutely positioned content inside a scroll container scrolls with it — once the bar was scrolled the white gradient sat in the middle of a chip ("Bruxelles ▯idi" in a phone screenshot). It is now a sibling on a non-scrolling wrapper, shown only while there is more to scroll (so the last chip is never faded), and a new station scrolls the bar back to its start, where the promoted, running trains are. `DynamicMap` passes `stationCoordsByName` for the distances. **The same name reaches every surface that names a train for a selected station**, or a chip reading "Bruxelles Midi – Milano" opened a panel headed "Milano → Bruxelles": `DynamicMap`'s `stationFirstFor` runs the same function over the same inputs (`selectedCityMatcher` is the bar's city test, shared) for the **line hover tooltip**, the **route chip** at the top of the map, and `firstDirectionByRoute`, which tells `TrainDetailPanel` which train to list first (`orderTripsStationFirst`, tried before the panel's older onward-stops guess, which stays as the fallback when the station is not in the route's stop names). A card's direction is `tripDirection` — its `direction_id` first, since that is what the panel already pairs a card with its row by, then a train number only one direction carries. The panel's synthetic trips (every tripless row: ICN, ES feed rows, Amtrak…) used to carry **no** `direction_id`, so every card read as direction 0 — and ICN 797's "Official timetable" link was built with 796's origin station (Salerno, for a train leaving Torino); they now carry it. Without a selected station nothing changes: the tooltip names the drawn direction and the chip the row's first. Covered by `npm run verify-bottom-bar`, which checks the naming against the real rows in the published payload.
- **Operator filtering:** Train4you is filtered at the API level. Use `isTrain4you()` from `src/lib/trainOperatorsFilter.js`.
- **Station coordinates** are stored in `src/data/stationCoordinates.js` as a lookup table and merged via `src/helpers/enrichStationsWithCoordinates.js`. The same table (`data/overrides/station-coordinates.json`) is now applied **at build time** in `normalizeStops()`, keyed on `stop_id` and `stop_name` like the payload projection, because applying it only in the browser meant the SEO corridor maps drew all of its entries at the coordinate it exists to replace — 78 stops across the published payload, Roma Termini and Katowice among them. - **A stop belongs to one journey, and both ends of it were answered by two sources at once.** `getStationTimesForTrain` hands `src/lib/seo/data.js` a feed trip's stops; the assembly then overrides the endpoint times from the gated viewMap row — but it overrode only *half* of each endpoint, so the origin kept the **feed's** arrival beside the **row's** departure and the destination the reverse. A journey does not arrive where it starts or depart from where it ends, so neither field means anything whatever its source; what they carried was a second trip's clock sitting inside the first trip's stop. Paris–Aurillac printed it plainly — `{"departure":"19:28","arrival":"18:27"}` on the origin — and it is exactly where the enrichment had *deliberately* refused the feed's 2-stop portion, so the page contradicted the decision one layer below it. Not a one-route slip either: **284 endpoints across 238 built connection pages**, every route where a feed supplies the stop list. The fallback branch a few lines down had always had it right (`departure: i === 0 ? … : ""`), which is the tell — two branches answering the same question differently. Covered by `verify-station-times`, which asserts it against the **built** pages, since the defect lives in the assembly rather than in either function, and pairs it with the inverse: clearing the endpoints must not cost the stops in between their times (3 469 of 5 912 intermediate stops still carry one, which is the whole reason to prefer a feed).
- **A row describes one train, so its times travel with its stop list.** Taking a trip's stops while keeping somebody else's times is not a compromise, it is a row that contradicts itself — and it did, until a hand-check of SNCF's timetables found it. Across the published payload **16 of 18 SNCF directions carried the feed's exact stop list beside Back-on-Track's endpoint times**, disagreeing on 16 of them and by an hour or more on 6, worst **183 minutes** (IC Nuit 3750: Back-on-Track 19:44→07:03 against the feed's 22:47→07:22, whose Souillac/Cahors/Montauban corridor the probe had already confirmed as the night train's). The connection page made it visible from both ends at once, since `getStationTimesForTrain` reads *every* `*-trains.json` and was already printing the feed's per-stop times under facts computed from Back-on-Track's. So the via verdict now gates `setTimes`, `updateEndpoints` **and** `stamp` together (`takesFeedTrip` / `tookAnyFeedTrip` in `enrich-view-map.mjs`): a row whose feed trip was refused keeps Back-on-Track's everything and is *not* stamped, because claiming corroboration for a row that kept none of the official data would tell the integrations dashboard a first-party source feeds a route it does not. `viaOnlyIfRicher` being off leaves every existing source exactly as it was. **Two silent faults had to be cleared before the switch did anything**, and both are the shape this repo keeps meeting — correct-looking until somebody turns the option on. `toHHMM` matched only a `T`-prefixed ISO time, which is what NightJet and European Sleeper emit; `gtfs-sleeper` writes a bare `"22:47"`, so `setTimes` would have been a **no-op for SNCF, Entur, Amtrak and VIA alike** and would have shipped as "fixed" having changed nothing (it now also accepts a whole-string `HH:MM`, anchored so a date can never be read as a time, and wraps a past-midnight hour). And `enrichViewMap` never passed `stopCoords` to `trainsByNumber` — only to `gtfsBundle` — so the incumbent via count fell back to the naive separator split, `"Mont-Dauphin - Guillestre"` read as two stations, and `viaOnlyIfRicher` refused an official list that was exactly as complete: **13 of 18 directions, silently**. With both cleared, 16 of 18 rows take the feed's trip and 14 directions are corrected. The two that stay are the Paris–Aurillac portions, a 2- and 3-stop stub the guard is there for. One number to treat with suspicion rather than trust: **IC Nuit 3970 runs 15h03 in the feed against its own counterpart's 11h51**, which is the signature of a portion timed until it is joined rather than the through train — the feed cannot say which, for the same reason it cannot attribute a service day (no `trip_short_name`, see the `sncf` bullet). Covered by `npm run verify-enrich`, which pins the fault too: with `toHHMM` back to `T`-only the accepted row keeps Back-on-Track's 19:44 instead of the feed's 22:47.
- **A via string is stations joined with `" - "`, and 437 stops have `" - "` inside their own name.** Splitting on the separator therefore does not merely lose a station, it *invents* two: SNCF's `"Rocamadour - Padirac"` arrived as "Rocamadour" and "Padirac", names no stop answers to, printed on the connection page as though they were places. The cost compounds down the whole chain, and the first link is the one nothing downstream can undo — `routeStationKeys` in `payload-projection.mjs` built the keep-set from the torn fragments, so all five affected stations were **present in the published artifact and absent from the shipped payload**; the browser never received them, and no amount of care in the map could have given them a marker. Beyond that: `deriveCities` linked neither half to the route (no map dot), the path builders found no coordinate (the drawn line skips a stop it runs through), and `viaOnlyIfRicher` counted the incumbent list as one station longer than it is, so a genuinely fuller official stop list was **refused** — exactly backwards for a guard whose job is "only replace with something fuller". This was the single largest cause of unresolved via stations in the payload: **28 of 59**, against 31 that are genuine spelling gaps. `splitViaString(via, isKnownStation)` (`src/lib/viaSplit.mjs`, dependency-free) walks left to right taking the longest run of atoms that names a real station; the predicate is injected because callers differ, and with none it degrades to exactly the old split, so a caller with no station table behaves as before. Two guards, both measured against the published payload before being written down: a merge happens only when the merged name **is** a known station, and not when **both** halves are themselves stations — that second one is a no-op today (14 merges qualify, 0 ambiguous) and exists so a station added later cannot start swallowing its neighbour. For the keep-set, `viaNameCandidates()` emits every reading instead, because keeping is a superset operation: an extra key matching no stop costs nothing, a missing one loses the station for good. The fault was one line copied into **twelve** places, and the twelfth is why the test asserts behaviour rather than grepping for the separator: `parseViaList` in `src/lib/seo/format.js` — the only copy whose output reaches a public page — hid from a search for `.split(" - ")` by using the regex `/\s+-\s+/` instead. That file's "no imports" rule is now one import, `viaSplit.mjs` being itself dependency-free, which keeps the property the rule was protecting. Covered by `npm run verify-via-split`, which pins the fault as well as the fix: reverting the projection fails it with the station missing from the shipped payload.
- **Route polylines** use `@mapbox/polyline` encoding. Route styling per operator is in `src/components/Map/utils/`.
- **A station selection shows the stops of the routes it draws, and no others.** A click gathers every route calling at the station by name, closed seasons included; `useRoutePaths` then skips a closed route when drawing, but `useMapMarkers` kept that route's stops as long as *any* route at the stop still ran, selected or not. Clicking Wien Hbf therefore showed Split, Knin, Maribor, Celje and Tychy with no line through them (ÖBB's EN 1272 Split–Wien, whose summer ended 26 September, and PKP's EN 1276 Rijeka–Warszawa), Graz drew nineteen line-less dots from Ostrava to Warszawa, and a click on 704 of 2 064 stations left at least one such dot. `selectedRoutesWithLines` (`routeStyleUtils.js`) is the one answer to "which selected routes are on the map" — the same `isRouteOutsideServiceIdSeason` the line builder uses — and the hook filters stops by it **before** grouping, so a grouped marker cannot anchor on a closed route's station either. The bottom bar and detail panel already dropped closed routes; the markers were the one surface that did not. Covered by `npm run verify:route-styles`, which also asserts the filter's place in the hook source.
- **Line style carries two separate facts** (`routeStyleUtils.js`, `MAP_LEGEND_LINE_BASE_STYLES`): the **dash** is cadence (solid = daily, `10,5` = sub-daily, `8,5` = ~weekly), and the **weight** is whether the route is real yet — every running route draws at `4.5`, and only a route that has never opened with no announced date (`hasUnknownStart`, e.g. ES Amsterdam–Milano "Postponed to 2027") drops to `2.75`. "Suspended" is not an unknown start. Cadence ranks from an explicit weekday list by **count**, so "Mon, Wed, Fri" and "Tue, Thu, Sun" draw alike. Synthetic rows have no `trips`, so `getRouteStyleFromFrequency` takes an optional row argument and ranks them from `service_id_0/1` — without it all 118 of them fall through to the daily default.
- **A timetable that has not begun draws faded, never hidden — and "not started" is not "finished".** `appendSyntheticRoutes` emits the next timetable period as its own row (`es_400_from_20261214`, `draw_as_active`, "… (from 14 Dec)") and its line is meant to show, because tickets are already on sale. Its **via stations** first rendered as ordinary green dots, so the same train appeared on two contradictory routings at once — December's via Eindhoven and Breda alongside today's via Aachen and Verviers — with nothing telling them apart. Dropping those dots instead was worse: the December Brussels–Milan line then ran visibly through Eindhoven and Breda with no markers on it, which reads as a bug rather than as a preview. So they render with `futureIcon` (`mapIcons.js`) — the intermediate-stop dot at `FUTURE_STATION_OPACITY`, with "Not yet running" in the tooltip and its own legend row. That constant is deliberately **not** the line's `MAP_LEGEND_LINE_BASE_STYLES.futureGhost.opacity` (0.35), even though it says the same thing: a 16 px dot carries far less ink than a 4.5 px-wide stroke crossing the map, so the same alpha reads much fainter on it and the dots all but vanished. `0.55` is what makes the dot say "not yet running" as loudly as the line does; the legend swatch reads the constant rather than hardcoding a class, so marker and swatch cannot drift. `useMapMarkers` therefore keeps **two** predicates apart: `seasonHasPassed` still drops stops (that route is over), while `isUpcomingPreview` only changes the icon. A selected station keeps its own icon — the user pointed at it, and the panel names the timetable. `upcomingPreviewRouteIds` (`routeStyleUtils.js`) is what marks the rows; `shouldHideRouteDueToFutureDate` cannot, since it reads `trips` and a synthetic row has none, so the dates come off the row's own `service_id_*`. **Both** of its conditions are load-bearing: `draw_as_active` alone also marks routes merely on sale early, and a future start date alone would have caught nine live routes — six Amtrak long-distance services whose GTFS feeds publish only the 2027 season, plus `es_400`/`es_401` themselves. Covered by `npm run verify:route-styles`.
- **A city name is not a location — on the selection side either.** Clicking a station gathers its routes in `handleMarkerClick` from every `cities[]` entry whose display name equals, or fuzzy-matches, the clicked one, and every station of every route it gathers then draws a marker. Both tests were name-only, so a click in Scotland reached **Glasgow, Montana** and put the Amtrak Empire Builder's whole stop list on the map (45 stations instead of 5); "Bar" in Montenegro reached **Boston Bar** in British Columbia and pulled in Toronto–Vancouver (86 instead of 19); Firenze picked up **Florence, South Carolina** — the same collision `groupCityMarkers` already guards against, one layer up. `stationsAreNearby` (`stationNameUtils.js`) now gates every one of those matches on `SAME_CITY_RADIUS_KM` = 60 km, the radius that function already uses. The threshold is not a guess: across the published payload the farthest legitimate pair is 44 km (Dąbrowa Górnicza ↔ its Ząbkowice station) and the nearest false positive 129 km (Sędziszów ↔ Sędziszów Małopolski, two different towns), so 60 km sits in a wide gap. A station with no coordinates is always kept — the guard rejects only what it can prove far apart. Covered by `npm run verify-station-selection`, which asserts both directions: the collisions are gone *and* the same-city variants the fuzzy matcher exists for (Lublin ↔ Lublin Zachodni, Lviv ↔ Lviv Pidzamche) still share their routes.
- **A cache written in an effect and read in a memo shows the previous data.** The memo runs during render, the effect after commit, and a ref write triggers no re-render — so `useRoutePaths`' `precomputedAllPathsRef` (there to make toggling "Show all routes" instant) served the *previous* payload's paths for as long as nothing else re-rendered. That collided head-on with the two-stage load: `/api/initial-data` lands without geometry, `/api/route-geometry` lands a moment later and `assemble()` rebuilds `viewMapData` with the polylines merged in (a new top-level object, and a new row for each of the **139** routes that gain geometry), the memo re-runs — and returned the stage-one paths from the unkeyed ref. Stage one can draw **1.7% of the ink**: 6 408 station-chain vertices against the real 368 452, and nothing at all for the 57 routes with no drawable chain. Selecting a route took the uncached branch and rebuilt correctly, which is exactly why clicking a line and closing the panel appeared to repair the map. The cache now carries the identity of every input it was built from (`allPathsCacheIsFresh`), so a stale one simply misses and the memo does the full build in that same render; the effect skips rebuilding what the memo just built, which also drops a duplicate pass over all 293 routes on every data change. `verify-payload-projection` pins it against the hook's source — the hook imports extensionless specifiers and cannot be loaded in raw node, and the defect is structural, so the structure is what there is to assert (the same reason `verify-via-schedule` asserts the panel's chain order). The other refs in the map are not this pattern: `useMapMarkers`' `previousZoomRef` is written inside the memo that reads it, and `cdTrainsCacheRef` is written beside a `setState` the render does see.
- **The marker list is recomputed on every pan and zoom frame, so its complexity is a feature of the map's feel.** `useMapMarkers`' memo depends on `mapZoom` and `mapBounds` — it has to, that is how viewport thinning works — which puts `thinStationsByViewport` in the frame budget. It was comparing every stop against every always-show rule, and the rule list is not the 40-entry curated allowlist it looks like: the caller appends **every endpoint of every route** (they must not vanish when zoomed out), so it is ~1 100 entries of which exactly one, `Frankfurt*`, is a prefix. 1 863 stops × 1 136 rules ≈ 2.1 million string comparisons a frame, and each stop was normalised **three** times (the loop, the allowlist test, `getStationScore`) through 45 regex replacements at 1.67 µs a call. Measured **19.3 ms a frame against a 16.7 ms budget** — every pan frame dropped, which is the "map lags when you drag it", and it got worse with every station an official stop list added. Exact rules now live in a `Set` and prefix rules in a list, the normalised id is computed once and passed down, and `normalizeStationNameForLookup` is memoised in `stationKey.mjs` (bounded, cleared wholesale — `buildAllRoutesPaths` already kept a local cache, which was this fix applied one caller at a time). **1.6 ms, a 12× cut**, with byte-identical output over 720 viewport/zoom/rule combinations and 59 840 normalizer inputs. `verify-marker-thinning` pins the *shape* rather than the clock: normalizations must stay linear in stops + rules, since a reverted `Set` blows that by three orders of magnitude while a wall-clock ceiling only wobbles with the runner.
- **A zoom must cost what is on screen, not what is in the world.** Over Poland a zoom step blocked the main thread ~2 s on a 4×-throttled CPU (production build), from three costs that each scaled with the whole dataset. (1) Every per-route trips question in `routeStyleUtils.js` scanned the whole trips table, and `useMapMarkers` asks one per route per station per zoom; `tripsForRoute` now answers from an index built once per trips table (WeakMap on its identity — the table is replaced, never mutated), and the hook caches the season answer per route per pass. (2) Thinning keeps every route endpoint in the world and, from zoom 8, every station — ~2 100 DOM markers to show ~80 — and Leaflet moves and restyles each one on every zoom; markers are now rendered only inside the viewport padded by one screen (`markerCulling.js`), a region recomputed on `moveend` only once the view leaves it, so an ordinary pan re-renders nothing. `mapBounds` (thinning) still updates on zoom only. (3) Leaflet re-projects every vertex of every polyline on every zoom (~370 000, twice: visible line + hit line). Route lines are `DecimatedPolyline` (`zoomDecimation.js`): per zoom, vertices under half a pixel from the last kept one are dropped (error ≤ 0.5 px, under Leaflet's own 1 px smoothing; cached per zoom), and only stretches within a screen of the view are projected, re-projecting on the `moveend` that leaves that window. Only the dash phase moves. The route `<Polyline>` elements are memoised so a zoom re-render does not `setStyle` ~600 lines. Result at 4× throttle: worst task per zoom 2.26 s → 0.16 s (markers only), 2.27 s → 0.33 s (all routes). Covered by `npm run verify-map-interaction`.
- **A grouped marker sits on a station, never at an average.** An average is not a place, and with one station in a name bucket it costs nothing — the moment a second arrives the dot slides into the countryside between them. Oslo is the case that showed it: the Entur enrichment put `Oslo Airport Gardermoen` into a via list, the bucket went from one station to two, and the Oslo dot moved **18.6 km** out of Oslo onto no station at all. `pickAnchorStation` picks the city's principal station and the marker takes both its position and its identity from it. Three rules, because the two obvious ones are each wrong somewhere: "the first non-via member" (the old identity rule) picks **Frankfurt's airport** and Berlin Gesundbrunnen, and "the most routes" picks **München Ost** over Hbf and Venezia Mestre over Santa Lucia. So: a name that declares itself principal (`Hbf`, `hl.n.`, `Centrale`, `Główny`, `Termini`, …) and among several the busiest; else the busiest station the city's trains **start or end** at, which is what fixes Oslo (Oslo S is an endpoint, Gardermoen is via-only) and is right where a city has no Hauptbahnhof by name — İstanbul Halkalı and Shanghai Songjiang really are where those trains call; else the busiest member. Direction words — Nord, Süd, Est, Ost, West — are deliberately **not** principal markers: they say where a station points, not what rank it holds, and including `nord` picks Bruxelles Nord over Midi and Paris Gare du Nord over Austerlitz. A route-count tie keeps the earlier member so the dot cannot flip between renders. Across the published payload this moves 37 of 42 grouped markers and lands **all 42** exactly on one of their own stations; the old custom-coordinate averaging ladder is gone, since the anchor's own coordinate already carries any `station-coordinates.json` override. `normalizeStationNameForDisplay` still buckets markers by substring, and `groupCityMarkers` used to put the grouped marker at the **average** of its members — so "Florence Amtrak Station" (South Carolina) joined Firenze Castello and Firenze Campo Marte and dragged the Florence dot to [40.6, −19.1], the middle of the Atlantic, leaving neither city a marker where it belongs. Each name bucket is now split into 60 km single-link proximity clusters first (`clusterByProximity`, reusing `distanceKm` from `returnGeometryBranches.js`), one marker per cluster. The radius is deliberately generous — Berlin-Spandau to Berlin Ostbahnhof is ~20 km — it exists to catch continents, not to second-guess city limits. Covered by `npm run verify-marker-grouping`.
- **A route is drawn as one line, never two.** Both directions carry geometry (`nj_polyline_0/1`, or a station chain per direction), and drawing both laid a second dashed stroke over the first: the dashes filled each other's gaps, so the line read solid and the cadence signal above was lost (it also read heavier, which is half the "too thick" story). The renderers (`buildAllRoutesPaths.js` + its twin in `useRoutePaths.js`) now draw direction 0, then only the stretches where direction 1 genuinely leaves it — `returnGeometryBranches()` (`src/components/Map/utils/returnGeometryBranches.js`), a 2 km-tolerance corridor test over a grid index, memoised per route. It **densifies** the outbound path first, because the tolerance is meant against the outbound *line*: a station chain's vertices can be 100+ km apart, and a return leg calling at extra intermediate stops sits far from every vertex while riding identical track. Over the published payload this leaves 311 strokes for 281 routes; the exact-reverse fast path (`arePositionsReverseEqual`) still short-circuits the common station-chain case. **A branch is drawn joined to the line, and a station chain's branch may be one stop long.** Each branch starts and ends with the on-corridor point on either side of the diverging stretch — without those anchors the return leg calling at Sinaia and Predeal drew as a stroke hanging in the air between Brașov and Ploiești, touching neither. And `minBranchPoints` (default 4, tuned for encoded polylines sampled every few hundred metres) is passed as 1 by the station-chain callers, because with one point per stop a single off-corridor station *is* the routing (Arad–Timișoara–Craiova on the way back where the outbound ran Brașov–Sibiu–Arad); dropping it left Romania's via stations as dots with no line through them. The lasting fix for those sparse chains is official stop lists — see the `cfr` source above. Covered by `npm run verify-return-branches`.

### Data Storage (committed JSON, no managed services)

All data is committed to the repo. Git is the database and the audit log.

**Layout:**
- `public/data/scraped/backontrack-{stops,view_ontd_map,trips}.json` — raw Back-on-Track datasets, refreshed nightly.
- `public/data/scraped/{nightjet,cd,chinese,italian,caucasus,curated,amtrak,viarail,europeansleeper,cfr,sncf,entur-vy,entur-sjn,entur-goa,trafiklab,jr-sunrise,srt,vnr,ktmb,uty}-trains.json` — per-source trains (`{ uploadedAt, trains: { "NJ 403": {polyline, stations, lastSeenAt}, ... } }`); filenames come from registry `output`. The `chinese` file is produced by `scripts/adapters/chinese.mjs` from the 12306 allowlist (`data/sources/chinese-sleepers.json`). The `amtrak`/`viarail` files are produced by the generic `gtfs-sleeper` adapter (`scripts/adapters/gtfs-sleeper.mjs` + `scripts/lib/gtfs.mjs`): it downloads an operator's official GTFS feed and keeps only the routes in a curated sleeper allowlist (`data/sources/{amtrak,viarail}-sleepers.json`), turning each into a synthetic route — feed shapes/stops/calendars mean no manual coordinates. The `europeansleeper` file comes from the same GTFS library through a dedicated adapter (see the registry section). Amtrak and VIA Rail stay empty until the first nightly scrape, since their feed hosts may be unreachable from a dev session's egress policy.
- `public/data/scraped/osm-{relationId}.json` — cached OSM relation geometries.
- `public/data/gtfs/pkpTrainShapes.json` — the PKP GTFS bundle the browser fetches directly. It ships **`rail_segments` only**: `parse-pkp-gtfs.js` builds `positions` as `railSegments.flatMap(s => s.positions)`, so shipping both made them byte-identical and cost 1.6 MB of the file's 3.3 MB. `hydratePkpBundle()` (`src/lib/pkpTrainKeyExtract.js`) rebuilds `positions` at the one point every reader passes through — the client, `verify-pkp-train-shapes`, `polish-routes.spec.js` — and is idempotent, so an older bundle that still carries the field is returned untouched. Anything reading the raw file must hydrate it first.
- `public/data/scraped/pkp-plk-trains.json` — PLK Open Data provenance/cache: `{ dataVersion, candidates }` — the fetched PLK stop-list candidates (per train, name/number + normalized stops) plus the schedule `/data-version` GUID that gates re-fetch. The actual enrichment is folded into `pkpTrainShapes.json` (see `pkp-plk` in the registry section).
- `public/data/published/initial-data.json` — the pre-merged, review-gated `{ stops, viewMap, trips }` payload served directly by `/api/initial-data` when fresh. Built by `npm run canonicalize`.
- `public/data/published/route-history.json` — per published route `{ firstSeen, lastSeen, lastChanged }`, projected from `seen.json` by `canonicalize`; the content-staleness signal behind the integration dashboard.
- `public/data/scraped/source-health.json` — per source `{ lastRunAt, lastSuccessAt, lastFailureAt, lastError, trainCount, consecutiveFailures }`, written by the scrape runner and merged across runs.
- `public/data/scraped/probe-health.json` — the same for price probes: per probe `{ adapter, lastRunAt, lastSuccessAt, lastFailureAt, lastError, attempted, found, consecutiveEmptyRuns }`, written by `probe-prices.mjs` and merged across runs. Exists because a probe that finds nothing is indistinguishable from a probe with nothing to report.
- `data/sources/registry.json` — the source registry (see above).
- `data/canonical/{routes/*.json, prices.json, state/seen.json}` — curated routes, per-route prices, approval index.
- `data/sources/official-sources.json` — the official-source research catalogue (see the integration dashboard above).
- `data/overrides/*.json` — manually editable lookups (station aliases/coords, operator pricing/booking, etc.), bundled via ESM JSON imports, edited in the admin panel.
- `data/proposals/` — exists only on the `proposals` branch (the review queue).

**Key modules:**
- **`src/pages/api/lib/file-store.mjs`** — disk reads over `public/data/scraped|published/`; generic `getTrainsBySource(file)`, `isFresh(uploadedAt)` (25h TTL).
- **`src/pages/api/lib/build-initial-data.mjs`** — pure registry-driven merge into the legacy `{ stops, viewMap, trips }` payload (+ seen gate + price stamping). Shared by `/api/initial-data` and `scripts/canonicalize.mjs`; `tests/verify-build-parity.mjs` is the golden test.
- **`src/pages/api/lib/github-content.mjs`** — GitHub Contents helpers (read/put/delete/list/branch, sha-conflict retry) used by all admin writes, the suggest endpoint, and the Actions scripts. Env: `ADMIN_GITHUB_TOKEN`/`GITHUB_TOKEN`, `ADMIN_REPO`/`GITHUB_REPOSITORY`, `ADMIN_COMMIT_BRANCH` (default main), `PROPOSALS_BRANCH` (default proposals).
- **`scripts/scrape-data.mjs`** — registry-driven runner (sticky-trains merge, registry-scheduled external steps, then the enrichment post-step from `scripts/lib/enrich-view-map.mjs` + synthetic leftovers). Daily GitHub Actions job (`.github/workflows/scrape-data.yml`, 3 AM UTC): scrape (incl. PKP GTFS) → classify → canonicalize → AI assist → (Mondays) price probes → auto-commit.

### Testing

Playwright E2E tests live in `tests/`. The config (`playwright.config.js`) auto-starts `npm run dev` on port 3000.

- **`tests/map.spec.js`** — basic map load and no console errors
- **`tests/smoke.spec.js`** — pre-commit smoke (homepage + API response)
- **`tests/data-integrity.spec.js`** — API data shape, known stations, no Train4you, operator-trains parity, OSM endpoint
- **`tests/suggest-api.spec.js`** — public suggestion endpoint validation/honeypot
- **`tests/map-data.spec.js`** — compares API stop/route counts against what renders on the map
- **`tests/verify-*.mjs`** — pure-logic suites runnable with raw node (see Commands); `verify-build-parity` asserts the merge is identical to the committed published artifact — run it after any change to `build-initial-data.mjs` or the registry.
- **`tests/verify-payload-projection.mjs`** — the first-paint payload budget: that every route-referenced station survives the stops projection (including the ones the browser-side PKP merge grafts on later), that the dead trip columns are gone and the live ones are not, that geometry round-trips through split → merge, that the committed PKP bundle ships one copy of its geometry, and that the whole thing stays under a 400 KB gzip ceiling.
- **`tests/verify-service-worker.mjs`** — the caching predicates in `public/sw.js`, evaluated in a `node:vm` context with `self` stubbed so the shipped file is the file under test: which paths are never cached (the admin page, not everything under `/data`), which take the stale-while-revalidate path, which stay cache-first, and that the staleness ceiling and cache version are sane. `const` bindings do not land on the sandbox object, so those are read back by evaluating the identifier — a destructure returns `undefined` and the assertion passes vacuously.
- **`tests/verify-bundle-tracing.mjs`** — the deployment-storage guard: that every API route has a row in `outputFileTracingExcludes`, that no helper under `pages/api/lib` is a `.js` file (which would deploy it as a route), that no key is a `'*'` wildcard (excludes run after includes, so it would delete them) or a bracketed `[id]` (picomatch reads it as a character class), that the loopback-only routes carry no dataset, and that no `/sitemap.xml` include is cancelled by its own exclude row. Shape, not byte count — the failure mode is a missing row, and nothing at build or request time complains about one.
- **`tests/verify-integrations.mjs`** — the integration dashboard: source resolution precedence, the priority formula, the headline totals against the committed payload, the catalogue's shape (every source needs a real URL), and the `official-sources` admin mutations.

Run a single test file: `npx playwright test tests/data-integrity.spec.js`
